## 詳細發現

### P0：A. 換手太晚（固定成本結構問題）

- 問題：每段工作都付這筆成本，而且和功能複雜度無關。context 越長，每一輪越貴；額度先燒完，就整段停工。
- 證據：見上表。新 session 開場約 63K～70K，代表換手本身的成本遠低於拖到 340K 的成本。
- 修法（改既有句）：workspace:unattended 的換手判準從「段收尾才換」改成「段收尾，或 context 超過門檻（先定 200K）時，在 commit 邊界換手」，不用 /compact。歸屬於 plugin，本次沒有 `--apply`，只列報告，同時轉交 plugharbor。
- 門檻怎麼算（和另一個整理 compact 用途的 session 對過）：
  - 新 session 接手後，第 10 輪 context 約 104K，第 40 輪約 137K，第 80 輪約 185K，大約每輪漲 1.16K（取 15 個超過 150 次呼叫的 session）。
  - 換手一次約等於 1M 讀取 token；一次 /compact 約 2.6M，而且壓完還停在 150K～200K，所以不用 /compact。
  - 每輪平均讀取量：門檻 150K 約 148K、200K 約 162K、250K 約 183K。理論最佳點在 150K 附近。
  - 先用 200K：換手次數比 150K 少一半，可以壓低換手後重查、重做的隱性成本；這項成本目前量不到。M-01 若驗出換手後前 10 輪沒有重工尖峰，再降到 150K。
- 自動壓縮維持 400K，只當最後一道防線。toolkit 的 context 提醒只給人看，agent 讀不到，所以換手判斷要寫進自動駕駛的迴圈。

### P1：B. 審查必修類別沒回饋到起草端

- 修法：把歷來重複的必修類別整理成一份自查表，放在專案層 `.claude/rules`，要求計畫起草者與實作者交回前逐項自查。

### P1：C. 顯示類缺陷改成自動檢查

- 修法：gate 加兩項檢查：四語缺鍵掃描、畫面不顯示原始代碼的測試；本機走查腳本對 820 寬度做溢出斷言。屬專案層，開成票。

### P1：D. rebase 沿用 CI 的判準

- 修法：rebase 後，若 `backend frontend shared scripts .github` 的 diff 和已綠的 commit 相同，就沿用那次 CI、不重跑；帳本已有 7 次是這樣做的，但沒有寫成規則。屬專案層。
