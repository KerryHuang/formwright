# 全站把「應用程式／套件」統一叫「積木包」（ux1 #139）
> 實作前檢查：✅ 2026-11-28（內容 87bb9bed）

來源：2026-11-27 全站 UI／UX 審查 P19；票 #139。受眾：一般（小企業老闆與行政）。

## 目標

「一包現成的模組設定」（CRM、進銷存、MES 這類）在介面、手冊、官網都叫「積木包」（使用者 2026-11-27 裁決）。另外修正積木包頁上按鈕的主次層級。

## 1. 用詞對照

| 舊詞 | 新詞 |
|---|---|
| 應用程式（指一包模組設定） | 積木包 |
| 套件、應用程式套件 | 積木包 |
| 範本套件 | 範本積木包 |
| 已關閉的應用程式 | 已關閉的積木包 |
| 應用程式代碼 | 積木包代碼 |

判定基準：句子裡的「應用程式」「套件」指的是可開啟、關閉、升級、匯入、匯出的那一包模組設定，就改。指別的東西就不改，例如「AI 用戶端」這類外部程式、作業系統的應用程式、npm 套件、設計器的「模組範本」。實作時逐筆判斷，不用全域取代。

外語對應詞（主控裁決，待使用者確認；官網只有繁中，沒有既有譯名可沿用）：

| 語系 | 單數 | 複數或標題 | 範本積木包 |
|---|---|---|---|
| en-US | block pack | Block packs | Template packs |
| th | ชุดบล็อก | ชุดบล็อก | ชุดบล็อกแม่แบบ |
| vi | gói khối | Gói khối | Gói khối mẫu |

外語句子照新詞改寫通順，四語的鍵集合要一致（`locales` spec）。

## 2. 範圍

### 2.1 要改

- **前端介面字串**：`shared/i18n/<code>/ui.json` 四語。繁中目前約 65 筆，分布在 `menu`、`dynamic`、`designer`、`demoData`、`apps`、`policies`、`approval`、`audit`、`localePacks`。只改值，**不改鍵名**。
- **後端寫死的使用者可見訊息**：一般使用者或管理員操作時會看到的，例如 `ActivateModuleHandler.ClosedMessage`「請由應用程式重新開啟或關閉」、開啟／關閉／刪除積木包時的阻擋訊息。實作時 grep `backend/src` 中雙引號字串裡的「應用程式」「套件」，排除註解。
- **前端程式裡寫死的繁中**：grep `frontend/src` 的 `.vue`、`.ts`（排除測試與註解）。
- **手冊** `docs/manual.md`：約 132 處「應用程式」、63 處「套件」，照判定基準改；章節標題改了以後，站內錨點連結（`#範本套件` 這類）要一起改，並 grep 全 repo 引用這些錨點的地方。
- **Demo 說明** `docs/demo.md`、`README.md` 給使用者看的段落。
- **官網** `site/index.html`：「內建的應用程式也是同一種積木拼的」改「內建的積木包也是同一種積木拼的」，「範本套件」改「範本積木包」。其他頁目前沒有舊詞。

### 2.2 不改

- 程式內部識別碼：API 路徑（`/apps`）、型別與類別名（`App`、`AppPackage`）、i18n 鍵名、`data-testid`、套件檔格式欄位（`manifest`、`requires.apps`）、檔名 `*.app.json`。
- **積木包格式驗證器的細部錯誤**（`AppPackageValidator*.cs`、`AppEffectsCodec.cs`、`AppReportCodec.cs` 裡「不在套件內」「引用了套件沒有的欄位」這類）：只有匯入自製積木包 JSON 的人會看到，訊息帶 JSON 路徑，讀者是寫套件檔的人。這類約 130 筆，改了要連動大量測試斷言，效益低。主控裁決，待使用者確認。
- 設計文件、roadmap、AGENTS.md 等內部文件：照舊，不追改歷史用詞。
- 內建積木包檔（`backend/apps/*.app.json`）裡的模組名稱與描述：裡面的描述若寫「應用程式」也要改（是使用者在積木包頁看得到的文字），但 manifest 結構不動。**只改描述不升版號**（審查後主控裁決 2026-11-28）：升級比對不看描述，純描述升版會讓既有安裝出現消不掉的「有新版」提示；積木包頁的描述直接讀目錄檔，不升版也看得到新文字（共用主檔如往來對象不在積木包頁列出，升版更沒有可見效益）。

## 3. 積木包頁的按鈕層級（P19）

`frontend/src/pages/system/AppsPage.vue` 每列右側的按鈕：

| 狀態 | 按鈕 | 樣式 |
|---|---|---|
| 未開啟 | 開啟 | 主要：`color="primary"` 實心（不變） |
| 已關閉 | 重新開啟 | 主要：實心（不變） |
| 已關閉 | 刪除 | 危險：`outline color="negative"`（不變） |
| 開啟中、有新版 | 檢視更新 | 次要：`flat color="primary"`（原本是 outline primary，看起來像主要動作） |
| 開啟中 | 關閉 | 次要：`outline`，文字與框用一般文字色（不是灰色），看起來可以按、不像停用 |

- 「關閉」的文字色用主題的一般文字色 token，不寫死色碼；淺色與深色主題都要和停用按鈕分得出來（停用按鈕是 Quasar 的 `disable` 透明度）。
- 同一列最多兩個按鈕，不收進「⋯」（#141 的門檻是 3 個）。
- 頁標題、小標「應用程式」照 §1 改成「積木包」。

## 不做

- 不改內部識別碼與 API。
- 不改格式驗證器的細部錯誤（§2.2）。
- 不改積木包頁的版面，只改按鈕樣式與文字。

## ERP 對照

用詞統一，不涉及主檔或單據。ERP 慣例裡相近的概念是 Odoo 的「Apps」、SAP 的「Solution package」；本產品採「積木包」是為了凸顯「打開來可以自己改」，和官網一致（使用者裁決）。

## 宗旨檢查（2026-11-28）

1. 機制還是政策：不適用，只改文字與樣式。
2. 寫死掃描：不適用，沒有新常數。
3. 單一來源：通過。介面文字都在 `ui.json`，後端訊息照既有寫法。
4. 兩個應用程式：不適用。
5. 空系統：通過。沒有開任何積木包時，積木包頁照常顯示「目前沒有可用的積木包」。
6. 套件只用定義組成：不適用。
7. ERP 對照：見上一節。
8. 權限與驗證：不適用，不改權限判斷。
9. 不限產業：通過。

## 驗收

### AC-01 繁中介面沒有舊詞 [ui]
#### 步驟
1. 以系統管理員 Demo 帳號登入，看側欄、積木包頁、積木包更新頁、Demo 資料頁、系統政策頁、稽核頁。
#### 預期
- 側欄項目是「積木包」；積木包頁標題、分區小標是「積木包」「範本積木包」。
- 上述頁面看不到指一包模組設定的「應用程式」「套件」。
- `shared/i18n/zh-TW/ui.json` 的值裡沒有「應用程式」「套件」，除了 §1 判定基準排除的用法（交付說明逐筆列出留下的鍵與理由）。

### AC-02 外語同步 [ui]
#### 步驟
1. 切換到 English、ไทย、Tiếng Việt，看側欄與積木包頁。
#### 預期
- 依序顯示 Block packs、ชุดบล็อก、Gói khối；範本區是 Template packs、ชุดบล็อกแม่แบบ、Gói khối mẫu。
- 四語鍵集合一致（locales spec 通過）。

### AC-03 關閉的積木包訊息 [ui]
#### 步驟
1. 到積木包頁關閉一個沒有被依賴的積木包（例如活動報名），再開它的模組列表。
2. 在動態模組設計對那個積木包的模組按啟用。
#### 預期
- 列表上方的唯讀提示寫「這個積木包已關閉」。
- 啟用被擋，訊息寫「請由積木包重新開啟或關閉」。

### AC-04 按鈕層級 [ui]
#### 步驟
1. 積木包頁，看一個開啟中、有新版的積木包，與一個已關閉的積木包，淺色與深色主題各看一次。
#### 預期
- 開啟中那列：「檢視更新」是無框的主色文字按鈕，「關閉」是一般文字色的外框按鈕，兩者都不像停用。
- 已關閉那列：「重新開啟」是實心主要按鈕，「刪除」是紅色外框。

### AC-05 手冊與官網用詞一致 [ui]
#### 步驟
1. 搜尋 `docs/manual.md`、`docs/demo.md`、`README.md`、`site/*.html` 的「應用程式」「套件」。
2. 點手冊裡改過標題的章節錨點連結。
#### 預期
- 剩下的都屬於判定基準排除的用法（交付說明列出）。
- 錨點連結都跳得到對應章節。

### AC-06 四寬度與深淺色 [ui]
#### 步驟
1. 積木包頁在 390、820、1366、1920 四種寬度與淺色、深色主題各看一次。
#### 預期
- 不橫向捲動；按鈕文字對比 ≥ 4.5:1。
