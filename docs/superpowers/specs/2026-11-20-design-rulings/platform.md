## A. 要問使用者（escalate），依「開工先後」排序

### 權限軸-漏1 「設計與授權拆兩條權限軸」排在哪裡開工
- 為什麼轉給使用者：條件 1（排序）。roadmap 段表有「權限軸」這一列，位置在 a4c 和 pg1 之間（兩段都已上線），但順序串（`docs/roadmap.md` 第 121 行）沒排它；核心設計 §15 把它列為「上線前必做」（Confirmed，`docs/superpowers/specs/2026-11-03-dynamic-modules-design.md:650-657`）。pkg1（套用含權限的新模組）和 mcp3（改權限工具）都要先有它。
- 題目：現在只要能改模組設計，就能在權限分頁替自己開任何模組的全部權限，包括看單價、解除欄位隱藏。修正這個洞的工作（另立「權限設定」權限、守衛、授予畫面，約兩個子單元）還沒排進開發順序。要排在哪裡？例：照現在的順序串，接下來是 o2d → p2、p3 → i3、i4 → mcp1 → O3 → pkg1 → au1。
- 選項：
  - A（推薦）O2 收完就做，排在 p2、p3 之前：工作量小（後端一段＋畫面一段），最早堵住洞，後面的 mcp1、pkg1、mcp3 都能直接沿用新權限。代價：p2、p3 和語系包往後延約一段。
  - B 排在 pkg1 之前（O3 之後）：等真的有人要用時才做。代價：洞多開一段時間；mcp1 期間做的權限相關畫面可能要回頭改。
  - C 第一個客戶上線前和「權限快取」一起做：兩件上線前必做一次處理。代價：pkg1、mcp3 開工時還沒有它，這兩段的權限題要先假設、之後回改。
- 什麼時候要答：o2d 收尾前；相依：先答這題，再答權限軸-3。

### 權限軸-3 哪些設定算「授權」，要有「權限設定」權才能改
- 為什麼轉給使用者：條件 6。擬題的推薦理由是「堵住直接放權的路徑」，但推薦方案仍留著至少一條讓設計者替自己拿到讀取權的路（Confirmed：簽核人會拿到臨時讀取權，簽核設計 a2c；`platform.md` 現況第 19 行），另外還有可能的間接路徑尚未查證（見下方「主控先查」）。留哪些已知缺口，是使用者對安全邊界的取捨。
- 題目：拆軸後，「改設計」的人不能再改模組權限分頁。但設計器裡還有幾種設定會間接決定誰看得到資料，要決定哪些也改成要有「權限設定」權。例：設計者小王想看「薪資調整單」，他沒有讀取權，但能改這張單的簽核流程。他把自己設成第一關簽核人，之後每張送簽的薪資調整單他都能臨時讀取。
- 選項：
  - A（推薦）模組權限分頁四塊（群組動作與資料範圍、個人權限、欄位權限、選項範圍）、共用主檔貢獻欄位的開放、開啟套件時的群組對應、「不提供給 AI」欄位旗標（mcp1b 起）歸「授權」；簽核人規則、狀態轉移的群組限制、共用檢視仍歸「設計」。設計者把自己設成簽核人這條路寫進手冊「已知限制」，稽核可查。代價：小王的例子做得到，只能事後從稽核發現。
  - B A 再加上「簽核人規則」：會給讀取權的只有簽核人，所以只把它收進授權；狀態轉移的群組限制只會收窄誰能推進單據，仍歸設計。代價：流程圖設計器的簽核人設定要依權限切唯讀，設計者改流程時要找權限設定者指定簽核人；守衛約多 5–10 個請求，不改表。
  - C 只要影響「誰能做」都歸授權（再加狀態轉移的群組限制）：最嚴。代價：流程設計幾乎都要兩個人一起完成，小公司每改一次流程就要找權限設定者；約 10 個以上請求加流程畫面唯讀。
- 主控先查（問之前補進題目）：「帶值」能不能把來源模組裡設計者看不到的欄位值，搬進他看得到的模組（Unknown）；彙總會計入所有子記錄、不看可見性（Confirmed，`docs/manual.md:427`），非金額型別的數字（例如設成「小數」的薪資）能不能藉此算出來（Likely 可以）。查到有路徑，就在 A 的代價補一句「另有 X 路徑」。
- 什麼時候要答：權限軸-a 開工前；相依：權限軸-漏1 之後，與 pkg1-4（套件群組對應）、mcp3-4 一致。

### pkg1-8 套用升級後出錯，怎麼回到原狀
- 為什麼轉給使用者：條件 6＋1。擬題的推薦方案是「預覽頁提示先匯出應用程式備份」，但這個前提不成立：應用程式匯出目前沒有畫面，只能由系統管理員呼叫 API 下載（Confirmed，`docs/manual.md:516`），而且匯出檔只有設計、沒有資料，同一個 id 已開啟時也不能再匯入（開啟回 409）。所以「從備份重建」實際上做不到；要不要為第一個客戶補還原能力，是範圍取捨。
- 題目：管理員把 CRM 從 1.3 升到 1.4、勾了 20 項套用，隔天發現報價單的折扣規則算錯了。現在沒有一鍵還原，也沒有畫面能先備份目前的設計。升級出錯時要怎麼回到原狀？
- 選項：
  - A（推薦）不做一鍵還原；預覽頁加「下載目前設計」按鈕（沿用既有匯出 API），套用後稽核逐項列出「舊值 → 新值」，出錯時照稽核到設計器手動改回。代價：要人工改回；改的項目多時費工。只在 pkg1d 多一顆按鈕與稽核明細，不改表。
  - B 提供「還原這次升級」：套用前存一份反向差異，N 天內（政策）可以反向套用，遇到之後又改過的項目就列為不能還原。代價：工作量接近 pkg1 本身；要多一張表存反向差異。
  - C 不做還原，靠資料庫備份還原：照部署文件做整庫備份。代價：還原會連同業務資料一起倒回，升級後輸入的單據會不見；備份還原畫面是階段 5 的事，現在只能找廠商。
- 什麼時候要答：pkg1c 開工前（pkg1a、pkg1b 不受影響）；相依：無。

### au1-5 系統管理員能不能用「忘記密碼」寄信重設
- 為什麼轉給使用者：條件 5。開放寄信重設等於新增一條接管帳號的路：管理員的信箱被盜，攻擊者就能重設管理員密碼。現在唯一管理員的救援方式是部署端設 `Auth__ResetAdminPassword` 再重啟（Confirmed，`docs/manual.md:28`、`docs/deploy.md:21`）；雲端版客戶碰不到部署設定，要找廠商。
- 題目：au1 要加「忘記密碼」寄重設連結。系統管理員也能用嗎？例：50 人公司只有老闆一個系統管理員，他忘了密碼。
- 選項：
  - A（推薦）可以，但已綁雙因素的管理員重設後登入仍要輸入驗證碼；重設後寄「密碼已被重設」通知，並對其他管理員發安全事件。代價：管理員信箱被盜，且管理員沒綁雙因素時，帳號就會被接管（搭配 au1-漏1 預設強制管理員雙因素，這個風險就小）。
  - B 不行，管理員只能由另一位管理員重設，或走部署端救援。代價：只有一位管理員的公司，雲端版要找廠商，地端版要找 IT 改環境變數重啟。
  - C 可以，但只限「已綁雙因素」的管理員；沒綁的走 B。代價：規則較難解釋，但風險最小。
- 什麼時候要答：au1b 開工前；相依：和 au1-漏1 一起問（答案互相影響）。

### au1-漏1 雙因素的出廠預設
- 為什麼轉給使用者：條件 1（雲端版的產品安全姿態與開站體驗）。使用者 11-17 只定了「可設強制或選用」，沒定出廠值。
- 題目：雙因素登入（手機驗證器 App 產生 6 碼）出廠時要怎麼設？例：新客戶第一次用 `admin` 登入，系統已經要求改密碼；如果預設強制管理員雙因素，他還要接著用手機掃 QR code 綁定，才能進系統。
- 選項：
  - A（推薦）出廠「選用」，但系統管理員一律強制（客戶可在政策放寬）。代價：第一次登入多一步綁定；沒帶手機的管理員當下進不去（復原碼見 au1-8）。Microsoft 365 的安全預設值就是強制管理員 MFA。
  - B 出廠「選用」，誰都不強制，由管理員自己決定要不要開。代價：開站體驗最順，但大多數小公司不會去開，管理員帳號只靠密碼。
  - C 出廠「強制全部使用者」。代價：最安全，但第一次推行時每個員工都要綁，客服量最大。
- 什麼時候要答：au1c 開工前；相依：和 au1-5 一起問。

### mcp3-5 AI 能不能開啟或關閉應用程式套件
- 為什麼轉給使用者：條件 1＋4。擬題推薦不提供，但 MCP 設計 §12 的 mcp3 驗收寫著「套用套件走兩段式」（Confirmed，`docs/superpowers/specs/2026-11-11-mcp-server-design.md:604`），`platform.md` 也把這條驗收列為已拍板；§7 大綱列了 `apply_app_package`、`close_app`（同檔 :405）。拿掉等於改驗收與範圍。
- 題目：要讓 AI 經 MCP 幫你開啟或關閉整個應用程式嗎？例：你跟 Claude 說「幫我開啟進銷存」，開啟會建十幾個模組並授權給你選的群組；關閉會讓整個應用程式變唯讀。
- 選項：
  - A（推薦）不提供，AI 只能讀應用程式清單與套件預覽，開啟、關閉由人到「應用程式」頁按；MCP 設計 §7 與 §12 驗收改寫。代價：少一個 AI 能做的事；開啟與關閉本來就很少做。
  - B 照原大綱提供，走兩段式確認碼，仍要系統管理員＋設計器權限。代價：確認碼擋不住會自動連續呼叫的 AI（MCP 設計 :328），等於 AI 可以自己關掉整個應用程式。
  - C 只提供「開啟」（建出來的模組先停在草稿），不提供「關閉」。代價：開啟流程要多一個「建成草稿」模式，工作量中等。
- 什麼時候要答：mcp3 寫設計前；相依：和 mcp3-4、mcp3-6 一起問（三題都是 mcp3 的範圍）。

### mcp3-4 AI 能不能改權限
- 為什麼轉給使用者：條件 1。MCP 設計 §7 大綱列了高風險工具 `set_module_permissions`（`mcp-server-design.md:405`），擬題推薦拿掉；C7（2026-11-12）只規定「改權限」若存在必須是高風險，沒規定要不要做。
- 題目：要不要讓 AI 替你改模組的權限？例：AI 建好「設備保養」模組後說「要我讓業務群組可以讀取、新增嗎？」
- 選項：
  - A（推薦）不提供；AI 只回建議設定（哪個群組、哪些動作），人到權限分頁按存檔。代價：每建一個模組就要人去授權一次。
  - B 提供，要求權杖擁有者有「權限設定」權，並走確認碼。代價：權限變更經過 AI；記錄內容裡藏的指令（提示注入）可能誘導 AI 放權限，確認碼擋不住自動連續呼叫。
- 什麼時候要答：mcp3 寫設計前；相依：權限軸-3、mcp3-5、mcp3-6。

### mcp3-6 AI 能改哪些設計範圍
- 為什麼轉給使用者：條件 1。MCP 設計 §7 大綱的一般寫入工具含 `set_workflow`（狀態機），擬題推薦流程類只讀不寫，屬於縮小範圍。
- 題目：AI 除了建模組、欄位、選項、規則、檢視、報表，還能不能寫狀態機、簽核流程、任務規則、連動事件、單據轉換、列印範本？例：「幫設備保養單加一個『待驗收 → 已結案』的狀態流程，只有主管能結案」。
- 選項：
  - A（推薦）模組、區塊、欄位、選項、規則、檢視、報表可寫；其他流程類只讀。代價：流程要人在畫面做；驗收「從零建兩模組」不受影響。
  - B A 再加狀態機與任務規則（照原大綱）。代價：狀態機含群組限制，會影響誰能推進單據，預演與驗證較複雜，工作量多約一個子單元。
  - C 全部可寫。代價：工作量最大；簽核流程圖改錯會影響簽核中的單據。
- 什麼時候要答：mcp3 寫設計前；相依：mcp3-4、mcp3-5。

## B. 顧問裁決（待使用者確認）

### 權限軸
- 權限軸-1 誰能授予「設計器」與「權限設定」：只有系統管理員能授予；權限設定者能改模組權限，但不能把這兩個權限給任何人 — 授權的最上層只有一個角色，才不會繞回自我提權；群組與使用者管理本來就只限系統管理員（Confirmed，`AccountService/Commands/SetGroupMembers` 等宣告 `ISystemAdminRequest`），一致 — 依據：使用者 11-11 裁決的目的、核心設計 §15、SAP 的角色維護與使用者指派分給不同人 — 可逆：放寬到 B 只改一條守衛。
- 權限軸-2 系統管理員自動擁有兩個權限：是，手冊改寫成跟程式一致 — 現行程式就是這樣（Confirmed，`PermissionResolver.cs:89`）；第一個管理員開箱就能用 — 依據：鐵則 4 空系統是合法起點 — 可逆：改 resolver 一行＋測試，不改表。手冊矛盾見 E。
- 權限軸-4 權限設定權全系統一份：是，不分模組 — 50 人以下公司管權限的通常一兩個人 — 依據：目標客群 — 可逆：之後要分模組加範圍表，不影響既有資料。
- 權限軸-5 設計者新建的模組，自己能不能用：不自動給，設計者用「預覽」分頁看表單，要試資料就請權限設定者授權 — 新模組預設沒人有權限，fail closed — 依據：鐵則 5（權限不 fail-open）、核心設計 §15 — 可逆：改成自動給只在建模組 handler 多寫一列，不改表。
- 權限軸-6 授予或收回這兩個權限發安全事件：比照 `admin.changed` 發安全事件（站內＋告警信）；一般模組權限變更只記稽核 — 這兩個權限等於半個管理員 — 依據：O2 既有安全事件模式 — 可逆：加減一個事件來源。
- 權限軸-漏2 權限設定者能不能改自己所在群組的模組權限、或自己的個人權限：可以，記稽核，不另發通知 — 權限設定者本來就是決定誰看得到資料的人，禁止改自己只會逼小公司多找一個人；拆軸要擋的是「設計者 → 授權」，不是「授權者 → 自己」。群組成員仍只有系統管理員能改 — 依據：權限軸段的目的（核心設計 §15）、目標客群 — 可逆：之後要職責分離時加一條「不能改自己」守衛，不改表。
- 權限軸-漏3 共用主檔模組的權限拆軸後誰能改：維持只有系統管理員（現行：主檔模組設計含權限只有系統管理員，Confirmed，`docs/manual.md:504`）；非管理員的權限設定者不能改主檔權限 — 不放寬既有邊界 — 依據：共用主檔設計、條件 5 不放寬 — 可逆：之後放寬只改守衛。

### pkg1
- pkg1-1 新版改了你沒動過的項目：列入、預設勾選，可取消 — 「你改過的預設不覆蓋」反過來就是「你沒改過的可以更新」，修正才送得到客戶手上 — 依據：使用者 11-17 裁決的方向；Odoo 升級更新沒改過的資料、`noupdate` 的不動 — 可逆：預設勾不勾只是畫面。
- pkg1-2 你改過、新版也改了：可以選用新版覆蓋，但預設不勾；勾選時並列「你的版本／新版」並提醒會被取代 — 符合「預設不覆蓋」，又不堵死 — 依據：使用者 11-17 裁決 — 可逆：只是畫面與一個旗標。
- pkg1-3 會影響既有資料的修改（改型別、改必填而舊資料沒填）：列出但不能勾，標原因與「請在設計器手動處理」 — 預覽時就知道哪些能套，不會套到一半失敗，也不自動改資料 — 依據：設計器既有守衛（簽核中、簽核鎖定），與 mcp3-3 共用同一張「是否影響既有資料」分類（見 D） — 可逆：之後放寬只改判斷。
- pkg1-4 新版的權限建議：新模組的權限照開啟時的群組對應一起套（預覽中可改對應，要有權限設定權）；既有模組的權限修改只列出、不提供套用 — 新模組沒有既有授權可衝突，既有授權是客戶的決定 — 依據：開啟套件已有群組對應流程、權限軸（群組對應歸授權，見權限軸-3 選項 A） — 可逆：只改套用規則，不改表。
- pkg1-5 這次略過的項目下次還列：會再列，標「上次略過」且預設不勾 — 基準快照就能判斷，不必新表 — 依據：簡單優先 — 可逆：要「永久略過」再加表。
- pkg1-6 匯入的套件也能用這個入口更新：可以，同一個 id 的新版走同一個預覽與套用 — 機制相同 — 依據：鐵則 3（兩個以上用途） — 可逆：入口多一個判斷。
- pkg1-7 同一個 id、來源不同要不要擋：擋，只接受同一來源標記的新版（內建只能被內建更新，匯入只能被匯入更新）— 防止匯入檔冒充內建套件改掉內建應用程式 — 依據：使用者 11-17 裁決「套件格式要帶來源標記」 — 可逆：改成只警告是放寬。注意：目前只分得出內建／匯入；兩份匯入檔是不是同一個發行者分不出來（沒有簽章），手冊要寫明，見 D。
- pkg1-漏1 「你改過」的判斷粒度：逐屬性判斷，畫面依物件分組顯示。例：你只把「交期」欄位的標籤改成「預計交貨日」，新版修了它的必填設定，這筆修正仍預設勾選；只有同一個屬性兩邊都改了，才算「你改過」 — 客戶最常做的就是改標籤，用整個物件判斷會讓大部分修正送不到 — 依據：使用者 11-17 裁決的目的；三方比對本來就要存完整基準快照，兩種粒度都算得出來 — 可逆：只改比對演算法，不改表。
- pkg1-漏2 只勾一部分時的相依：勾一項時自動帶上它依賴的項目並提示（例：勾了用到新欄位「付款條件」的規則，就連欄位一起勾）；取消一項時，依賴它的項目一併取消並提示 — 避免套出引用不存在物件的半成品 — 依據：開啟套件既有的相依檢查 — 可逆：只是預覽邏輯。
- pkg1-漏3 已關閉的應用程式：不能升級，要先重新開啟 — 關閉代表唯讀，升級是寫入 — 依據：套件設計關閉語意 — 可逆：之後要開放只改一個判斷。
- pkg1-漏4 新版移除的項目：列在預覽的「新版已不再使用」區，只告知、不能勾，你的系統照舊保留 — 落實「只新增不刪除」 — 依據：使用者 11-17 裁決 — 可逆：只是畫面。

### au1
- au1-2 Email 誰填、要不要驗證：管理員在使用者管理填，立即生效；本人可在個人設定改，新信箱要收驗證信點連結才生效，並寄通知到舊信箱 — 信箱是重設密碼的鑰匙，換信箱必須證明擁有新信箱 — 依據：OWASP、業界常見做法 — 可逆：拿掉驗證是放寬；反向要加欄位，所以第一版就帶待驗證欄位。
- au1-3 Email 唯一與忘記密碼的輸入：Email 可重複；忘記密碼頁輸入「帳號」 — 小公司共用 `office@…` 常見 — 依據：目標客群 — 可逆：改唯一要先清重複資料再加索引。
- au1-4 忘記密碼的回應與限制：一律回「若帳號存在且有 Email，已寄出重設信」；連結單次有效；效期（出廠 30 分鐘）、同帳號每小時次數（出廠 3 次）做成政策；重設後所有 session 失效並寄通知信 — 不讓外人拿登入頁探測帳號 — 依據：OWASP Forgot Password Cheat Sheet、鐵則 2 — 可逆：只改訊息與政策。
- au1-6 雙因素強制範圍：政策兩種狀態「選用／強制」，強制時可選「全部使用者」或「指定群組」，系統管理員一律在強制對象內；不另設「關閉」 — 使用者 11-17 只定了「強制或選用」，分群組可以逐步推行 — 依據：使用者 11-17 裁決、Microsoft 365 依群組套條件式存取 — 可逆：只改政策型別。出廠值見 au1-漏1。
- au1-7 被強制但還沒綁定：登入後直接進綁定畫面，綁好才能用；寬限天數是政策（出廠 0＝立即）；寄信重設密碼後登入仍要輸入驗證碼 — 忘記密碼不能繞過雙因素 — 依據：鐵則 2 — 可逆：只是出廠值。
- au1-8 手機遺失怎麼救：綁定時給 10 組一次性復原碼（可重新產生）；系統管理員可在使用者管理「重設雙因素」，寫稽核並寄通知給本人；重設別的管理員時另發安全事件 — 兩條路互補 — 依據：GitHub、Google 的做法 — 可逆：拿掉其中一條。
- au1-9 「這台裝置 N 天內不再問」：提供，天數是政策（出廠 30 天，0＝關閉）；改密碼、重設雙因素時全部失效 — 不提供時推行強制阻力大，客戶要嚴格可設 0 — 依據：鐵則 2、Google／GitHub 常見做法 — 可逆：改出廠值。
- au1-10 雙因素和 MCP 權杖：建權杖時重新輸入密碼，已綁雙因素的人另要輸入驗證碼；權杖照常使用；重設雙因素不撤銷權杖 — 建立時把關、使用時靠權杖的到期與撤銷 — 依據：MCP 設計 §5.1 — 可逆：改一個 handler。
- au1-11 管理員替別人重設密碼：兩種都留，對方有 Email 時預設寄重設連結，也可直接設臨時密碼（下次登入強制改） — 沒有 Email 的帳號（例如共用工作站的現場人員）仍要有路 — 依據：現行 `ResetPasswordRequest` — 可逆：畫面與一個請求。
- au1-漏2 部署端緊急救援同時清掉 `admin` 的雙因素：是，`Auth__ResetAdminPassword` 重設密碼時一併清除雙因素與記住的裝置，登入後重新綁定，log 留 Warning — 能改部署設定的人本來就掌握整台主機；不清的話，唯一管理員手機與復原碼都遺失就無路可走 — 依據：現行救援流程（`docs/manual.md:28`） — 可逆：一個判斷。
- au1-漏3 帳號信能不能自訂內容：第一版不能，用內建四語範本，寄件名稱與信中公司名稱讀站台主題設定 — 信件文字不屬業務政策 — 依據：簡單優先 — 可逆：之後加範本設定不影響佇列。

### mcp3
- mcp3-1 AI 建模組的主路：以「整份定義」為主（套件格式，先驗證與預覽，同意後一次建成草稿），細部修改用逐項工具 — 中途失敗不留半成品，人看得到全貌 — 依據：MCP 設計 §7「先產出完整定義、一次預演，再逐步套用」 — 可逆：工具面取捨，不改表。
- mcp3-2 AI 能不能啟用模組：不能，AI 只能建草稿，啟用由人在設計器按 — 草稿不影響任何人，啟用才會出現在全公司選單 — 依據：確認碼擋不住自動連續呼叫（MCP 設計 :328） — 可逆：工具登記。
- mcp3-3 AI 能不能改已啟用、已有資料的模組：可以，但只開不影響既有資料的修改（加欄位、改標籤、加選項、加規則、加檢視與報表）；改型別、刪欄位走高風險確認碼；簽核中與簽核鎖定的守衛照舊 — 日常小改是 AI 最大的用處 — 依據：設計器既有守衛；分類表與 pkg1-3 共用 — 可逆：分類是程式登記，不改表。
- mcp3-7 AI 做的設計變更要不要在設計器標記：不標，稽核表已記通道＝MCP — 不必改表 — 依據：O2 稽核表與 MCP 共用 — 可逆：要標記再加欄位。
- mcp3-8 設計器工具另有開關：加政策「允許 AI 設計器工具」，出廠關閉；關閉時建權杖畫面不列 `design.*`，既有權杖呼叫回 403 — 設計變更影響全系統，讓管理員明確選擇開啟 — 依據：fail closed、MCP 政策模式 — 可逆：一條政策。
- mcp3-漏1 AI 改的設計，pkg1 怎麼看待：跟人在設計器改的完全一樣。AI 在已開啟應用程式的模組加了欄位或改了標籤，pkg1 升級時就算「你改過」；AI 新建的模組不屬於任何應用程式，升級不碰 — 兩條路都走同一套設計器指令，不另立特例 — 依據：鐵則 1、MCP 設計 §4.4 — 可逆：不涉及資料。

## D. 主控技術決定

### 權限軸
1. 新代碼不能叫 `DYN00001`，因為業務模組從 `DYN00001` 起編（Confirmed，`SeedData.cs:20-38`、`IProgramRepository`）；改用不會撞號的值（例如 `SYS00001`），在 `SeedData` 建立。
2. 新增 `IPermissionAdminRequest`＋behavior，fail closed，回傳型別檢查比照 `DesignerAccessBehavior`。
3. `SaveModulePermissionsRequest` 改宣告要求權限設定權；`GetModulePermissions` 讓設計者可讀、不可寫；主檔貢獻開放、套件群組對應依權限軸-3 的答案改宣告；`IMasterDesignRequest` 的主檔規則不變。
4. 套件開啟與「從範本建立」會寫群組權限，要求兩條軸都有。
5. 既有資料遷移：沒有任何人被授予過 `DYN00000`，不自動給任何人權限設定權。
6. 前端 `GetMe` 回傳多一組 `permissionAdmin` 動作，權限分頁依它切唯讀。
7. 授予兩個代碼的 API 宣告 `ISystemAdminRequest`（依權限軸-1）。

### pkg1
8. 開啟時存基準快照（套件全文），套用後基準前進到新版。
9. 每個套件物件補穩定代號（欄位、選項、規則、檢視、報表、流程、轉換），改寫套件設計 §12 決策 10；需要 migration。
10. pkg1 之前已開啟的應用程式（只有 Demo）以目前版本號對應的內建套件檔補登基準；找不到就全部當「你改過」。
11. 跨版本以新版對基準直接比對，不逐版重播。
12. 套用逐條走既有設計器指令，全部包在一個交易；`formatVersion` 升一版，放版本與來源標記。
13. 相依的應用程式（主檔、整合）一起比對；新版要求的相依沒開啟，預覽列為不能套用。
14. 權限：比照開啟，要求系統管理員＋設計器修改；含群組對應的項目另要求權限設定權。
15. 預覽到套用之間用基準版本＋各模組 RowVersion 做樂觀鎖，期間有人改設計就要求重新預覽。
16. 簽核中、簽核鎖定的模組照設計器既有守衛擋下。
17. 「是否影響既有資料」的設計器指令分類只寫一份，pkg1-3 與 mcp3-3 共用（鐵則 3）。
18. 來源標記只分內建／匯入；匯入套件的發行者欄位只是自我宣稱，不當成防偽依據，手冊寫明。

### au1
19. 帳號信佇列沿用 `Dynamic_AlertOutbox` 的「領取 → 交易外寄 → 記結果」模式，但用另一張表或 `Kind` 欄區分；不套節流與摘要；資料庫寫不進時不直送。SMTP 連線設定照使用者 11-19 裁決搬到核心（見 E）。
20. 重設權杖只存雜湊，128 位元隨機，單次使用；連結網址改用核心的 `App:PublicUrl`，保留 `Ops:PublicUrl` 舊鍵相容；沒設定就停用「忘記密碼」並在設定頁提示。
21. 忘記密碼另設一組降速（同 `LoginThrottle` 模式），回應時間固定。
22. TOTP 照 RFC 6238（SHA-1、6 碼、30 秒、容許前後一個時間窗、同一碼不能重用）；密鑰用 Data Protection 加密；PostgreSQL 部署要設持久的 `KeysDirectory`，部署文件寫成必設。
23. 登入第二步：密碼通過後發短效「待驗證」cookie，驗證碼錯誤計入降速。
24. `Demo:LoginEnabled` 開啟時：寄信設定唯讀，忘記密碼與雙因素停用。〔2026-11-21 更新：「忘記密碼與雙因素停用」已由 au1 設計 §13（Demo 收件匣＋mfa01 示範）取代；寄信設定唯讀保留。〕
25. 密碼最短長度從常數 `ChangePasswordValidator.MinLength` 改成政策（出廠 8），依鐵則 2。
26. 通知信語系用使用者的介面語系，沒有就用系統預設語系。
27. QR code 在前端產生，選 MIT 授權的套件。
28. 使用者管理清單顯示每個人有沒有綁雙因素、Email 是否已驗證。

### mcp3
29. 整份定義的輸入直接用最新 `formatVersion` 的套件格式；驗證錯誤回 JSON path 與訊息代碼，讓 AI 能自己修。
30. 預覽是唯讀工具，不需確認碼；建立是一般寫入，帶冪等鍵，在一個交易內重播設計器指令（沿用「從範本建立」）。
31. 工具描述與回傳裡的模組名稱、選項標籤當不可信資料包起來（MCP 設計 §9.1）。
32. 每個寫入工具宣告對應的 `IDesignerRequest` 動作，權限檢查完全交給既有 behavior。
33. 稽核：整份建立記一筆總紀錄，加每條指令的子紀錄（用 request id 串起來）。
34. 設計器寫入工具另設較低的每分鐘上限，整份定義也設大小上限（模組數、欄位數）；這兩個屬於技術限制，列進可寫死清單給使用者看過。驗收用 Claude Code 與 Codex 各跑一次「從零建兩模組」。
