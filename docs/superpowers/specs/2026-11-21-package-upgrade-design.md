## 1. 目的

客戶開啟內建應用程式（例如「CRM 與銷售」1.3.0）之後，模組、欄位、規則、權限都屬於客戶，客戶可以自己改。現在 Formwright 修正或加強了內建套件（1.4.0 補了一個欄位、修了泰文譯名、加了一份報表），這些修改送不到已開啟的客戶手上：同一個 `manifest.id` 不能再開，也沒有任何更新的 API（套件設計 §12 決策 2、3）。路線設計把它列為「第一個客戶正式上線前必須決定」。

pkg1 做一個**升級預覽與逐項套用**的入口：

1. 開啟應用程式時保存一份套件原文當**基準**（使用者裁決 2026-11-21，推翻套件設計決策 15）。
2. 有新版時，用「基準、新版、客戶現況」三方比對，列出每一項差異，分成「只有新版改」「只有客戶改」「兩邊都改」三類（使用者裁決 2026-11-21），另外標出新版新增、客戶已刪除、新版移除。
3. 管理員逐項勾選要套用的項目；**只新增不刪除，客戶改過的項目預設不覆蓋**（使用者裁決 2026-11-17）；多語文字依語系合併，不整段蓋掉（語系包設計 §18 第 7 點）。
4. 套用後基準換成新版原文，下次升級從這裡比起。

這是平台機制：任何應用程式套件（內建三套、共用主檔兩套、客戶匯入的）都走同一條路，沒有替哪個應用程式寫特例。

## 2. 範圍

**範圍內**

- 基準：新表 `Dynamic_AppBaseline`，開啟（含自動開啟的共用主檔、Demo 產生器）時寫入套件原文、群組對應、開啟時排除的欄位（§5）。
- 三方比對引擎：把基準、新版、客戶現況都換成同一套「比對項目」再比，多語文字逐語系比（§6）。
- 預覽 API 與套用 API（§8），套用在一個交易內、整批成功或整批回滾。
- 涵蓋套件格式的全部 section：應用程式資訊、模組、區塊、欄位、選項、規則、共用檢視、群組、模組權限、欄位例外、選項範圍、報表、狀態機、單據轉換、連動事件、跨記錄檢查、分錄、列印範本、任務規則、簽核流程、共用主檔的貢獻、整合（§6.2）。套用分兩段上線（§15）。
- 新版的來源：內建套件隨程式部署（`backend/apps/*.app.json`）；匯入的套件可以再匯入較新版本（§7）。
- 畫面：應用程式頁顯示「有新版」，獨立的更新頁（§10）。
- Demo：CRM 以一份「較舊版本」開啟，示範三類差異、預設勾選與被擋（§11）。

**範圍外**

- 刪除或停用客戶的任何東西。新版移除的項目只列出（Q4）。
- 改欄位型別、模組種類（獨立／擴充）、擴充宿主、欄位所在區塊與排序：列為「無法套用」或不比對（§6.4）。
- 已建立群組的改名與成員（群組屬於客戶的組織，§6.2）。
- 自動更新、排程更新、一鍵全部套用而不預覽。
- 降版（新版版號比基準小，§7.2）。
- 一鍵還原這次升級：不做。預覽頁可以先「下載目前設計」，套用後稽核逐項記「舊值 → 新值」，出錯時照稽核到設計器改回（使用者 2026-11-20 確認，分流 pkg1-8 選項 A；§9.3、§10.2）。
- 範本（單模組範本，`TemplateService`）的更新：範本建出的模組不屬於任何應用程式，維持「範本改了不跟著更新」（手冊已知限制，核心設計 §15 第 49 條）。
- 套件格式變更：pkg1 不升 `formatVersion`（T10、§13）。
- 規則與檢視加持久代號（Q7 的替代方案，列 💡）。

## 4. 已定決定（本設計照用，不再問）

- **升級預覽列出新版與客戶現版的差異，管理員逐項選擇套用，只新增不刪除，客戶改過的項目預設不覆蓋；套件格式要帶版本與來源標記**（使用者裁決 2026-11-17）。「來源標記」的解讀見 Q9。
- **開啟應用程式時保存一份套件原文當基準**，推翻套件設計決策 15（使用者裁決 2026-11-21）。
- **預覽分「只有新版改」「只有客戶改」「兩邊都改」三類，兩邊都改時顯示原值**（使用者裁決 2026-11-21）。
- **pkg1 上線前開啟的應用程式沒有基準，一律當「可能改過」、預設不勾**（使用者裁決 2026-11-21）。本設計解讀為：沒有基準時，所有和新版不同的項目（含新版有、客戶沒有的）都預設不勾，標「沒有基準，無法判斷」。「新版新增也不勾」這半句是顧問拍板，待使用者確認。現在沒有正式客戶，Demo 每天重建，實際上只有開發機與測試庫會遇到。
- **多語文字依語系合併**（語系包設計 §10.5、§18 第 7 點）：客戶自己匯入的日文不會被新版的四語蓋掉。
- **套件內容只要求繁中**（p3 判斷 12）：套用時照開啟的做法進 `PackageTextScope`，不跟政策 `locale.requiredText`。
- **「不提供給 AI」旗標只加不減**（i3 §8.1，使用者裁決 2026-11-21）：i3c 合併後，升級遇到這個旗標照同一條規則。
- **開啟、關閉、重新開啟、刪除要系統管理員加設計器權限**（套件設計決策 7）：升級比照開啟。
- **2026-11-19 平台分流 pkg1 各題**（使用者 2026-11-20 確認）：沒改過的預設勾（pkg1-1）；兩邊都改可勾、預設不勾、並列兩版（pkg1-2）；會影響既有資料的修改列出但不能勾（pkg1-3）；既有模組的權限修改只列出、新模組的權限照群組對應一起套、預覽可改對應（pkg1-4）；匯入的套件走同一個入口（pkg1-6）；不跨來源（pkg1-7）；不做一鍵還原、可下載目前設計、稽核逐項記舊新值（pkg1-8）；逐屬性判斷（漏 1）；相依連勾（漏 2）；關閉的不能升級（漏 3）；新版移除只告知（漏 4）。
- **使用者裁決 2026-11-21**：略過的項目下次再列、標「上次略過」、預設不勾（Q3，pkg1-5）；規則整組比對、檢視用名稱對應（Q7）；來源標記不改格式（Q9）。

## 5. 資料模型與 migration

### 5.1 基準表（T1）

新表 `Dynamic_AppBaseline`（實體 `AppBaseline`），一個應用程式一列：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `AppId` | bigint，主鍵，FK 到 `Dynamic_App`（cascade） | 刪除應用程式時一起刪 |
| `PackageJson` | text | 套件原文（§5.2） |
| `GroupMapJson` | text，NOT NULL，C# 預設 `"{}"` | 套件群組代號 → 群組 id；略過的群組值為 `null`（§5.3） |
| `ExcludedFieldsJson` | text，NOT NULL，C# 預設 `"[]"` | 開啟時取消勾選的限定欄位名（`OpenAppBody.ExcludeFields`） |
| `SkippedJson` | text，NOT NULL，C# 預設 `"[]"` | 上一次升級列出、可以勾卻沒勾的項目：項目識別、屬性（含語系）、當時客戶的值（舊值）、當時新版的值（§9.2，Q3） |
| `CapturedTime` | 牆上時間（`timestamp`） | 寫入基準的時間（開啟或上一次套用升級），取 `IBusinessTime.Now`，和 `AuditableEntity.CreatedTime` 一致 |

- 不另存版號與格式版號：版號判斷只用 `App.PackageVersion`（§7.2），格式版號在原文裡；多存一份只會多一個可能分歧的來源（審查建議 4）。三個 JSON 欄比照 `AppIntegration.ItemsJson` 設 `IsRequired()`。
- 放獨立的表、不加在 `Dynamic_App`：`App` 在選單、權限、匯出等地方常被整列載入，原文最大 1 MiB，不該跟著每次載入。
- 不留歷史：只存目前的基準。升級前後的版號與套用項目數記在稽核（§9.3）。
- SQLite 與 PostgreSQL 各一份 migration `AppBaselines`（`scripts/db/add-migration.sh AppBaselines`），只建表、不搬資料：既有應用程式沒有原文可搬，照 §4 當「沒有基準」。PostgreSQL 的 text 欄照 PostgreSQL provider 設計 §5.4 的慣例（`text`，不用 `jsonb`）。
- `Dynamic_App` 不加欄位：有沒有基準看這張表有沒有列。

### 5.2 存原文，不存解析後的物件（T2）

- 匯入的套件：存 `Dynamic_AppPackage.Json` 那份原文（含 v1 範本檔）。
- 內建套件：`AppCatalog.Load` 改成同時保留每個檔案的 UTF-8 原文（去 BOM），開啟時存這份。
- 讀基準一律走 `AppPackageSource.ReadAsync`：舊格式在記憶體升級、不回寫（套件設計 §4.9 的既有做法）。所以基準是格式 8、新版是格式 9 時照樣能比：兩邊都讀成同一個 `AppPackageData`。
- **例外：v1 範本檔**。v1 升級時跨應用程式引用依「當下已知的套件」解析（`AppPackageUpgrader.FromTemplate(…, KnownAsync)`），§7.3 允許取代匯入套件之後，同一份 v1 原文在不同時間可能讀出不同結果，比出假差異。所以來源是 v1 時，基準存**開啟當下升級後的 v2 序列化結果**（`TemplateJson.Options` 寫出、`formatVersion` 為當時的目前版），之後照一般 v2 原文讀。v2 以上的原文不受已知套件影響，照存原文。
- **Demo 推導的舊版**（§11.1）：推導產出的文字就是這次開啟的原文，基準存這份推導文字，不存目錄檔。
- 為什麼不存匯出結果或解析後重新序列化的 JSON：原文才是「Formwright 當初發的那一版」，往後讀取器改版時照樣讀得懂；序列化結果會隨程式改版而變，變了就會比出不存在的差異。

### 5.3 群組對應（T3）

開啟時 `OpenAppBody.GroupMap` 的結果（`map` 對到的群組 id、`create` 新建出來的群組 id、`skip` 與沒列出的記 `null`）存進 `GroupMapJson`。共用主檔自動開啟時存它自己那份（`OpenAppBody.Masters[id]`）。

用途：比對權限、欄位例外、選項範圍、報表分享、狀態機轉移的群組、簽核關卡的群組時，把套件的群組代號換成客戶系統裡的群組（正規化規則見 §6.2.1）。群組事後被刪除，對照就失效，那個代號在預覽裡當成「新群組」重新請管理員對應（§8.1）。對到 `null`（開啟時略過）的代號不算失效，維持略過；新版的新模組或新物件用到它時，預覽的群組段列出它、可以改成對應或新建（§8.1、§10.2，分流 pkg1-4）。

### 5.4 誰寫基準

- `AppOpener.OpenCoreAsync`（`AppService/Commands/OpenApp.cs`）在寫入 `Dynamic_App` 之後寫基準；HTTP 開啟、自動開啟共用主檔、Demo 產生器都走這裡，不必各寫一次。
- 套用升級成功時整列換成新版（§9.2）。
- 重新開啟、關閉不動基準；刪除應用程式時隨 cascade 刪掉，之後再開就是新的基準。
- 共用主檔再匯入合併（共用主檔設計 §9）不動基準：合併補進來的欄位在比對時是「客戶現況有、基準沒有」，照 §6.3 的規則處理。

## 6. 三方比對

### 6.1 三個輸入

| 輸入 | 從哪來 |
|---|---|
| 基準 B | `Dynamic_AppBaseline.PackageJson` 讀成 `AppPackageData` |
| 新版 N | 候選新版（§7.1）讀成 `AppPackageData` |
| 現況 C | `AppExporter` 的「比對模式」匯出（T4）：含停用欄位（`includeInactive: true`）；只帶有對照列的項目（§6.3）；表達不了的引用不略過，該項目標「無法比對」。匯出整份失敗（`Exported.Errors` 不為空，例如簽核流程表達不了）時，預覽回 `canApply: false` 與 `blockers`（帶匯出的錯誤），不是 500 |

三者都換成同一組「比對項目」（`UpgradeItem`：項目識別、屬性表）再比。比對不是拿 JSON 文字直接比：每種項目有自己的正規化，例如欄位的 `config` 先解成 `FieldConfig` 再去掉預設值，`null`、省略、空陣列視為相同。

**必須成立的不變式**（§17 的 U1）：任何內建套件開啟後立刻拿同一版預覽，差異是零。這條擋住「正規化不一致比出假差異」，是本設計最大的風險（§18）。

說明（表格外）：

- **權限只跟著新東西走**（分流 pkg1-4，使用者 11-20 確認）：新模組的權限照群組對應一起套；既有模組、既有欄位、既有選項的權限修改只列出、不能勾（`applicable: false`，原因「權限是你的授權決定，請到權限分頁調整」）。理由：新模組沒有既有授權可衝突，既有授權是客戶的決定。既有模組上新加的欄位、選項、貢獻，附帶的權限跟著新物件一起套，含給權類（使用者裁決 2026-11-21，Q12）。
- **附帶權限記在應用程式名下、關閉時收回**（Q12）：給權類（貢獻的模組權限、貢獻欄位的可見列）一律寫成 `GrantSource.App`＋本應用程式的 `AppId` 的來源記錄（`MasterGrants.GrantAsync`、`FieldGrant`），應用程式關閉時寫入類授予不再計入（`MasterGrants.Counts`）。一般模組上的新欄位、新選項只會帶限制類（欄位隱藏／唯讀、選項範圍），沒有給權類；那個模組本身屬於應用程式，應用程式關閉時模組變 `Closed`、整個唯讀，不需要另外收回。

- 識別用套件代號，不用名稱；客戶改名不影響對應。檢視是例外（沒有代號），用繁中名稱，客戶改名的檢視會被當成「客戶已刪除」加上一份客戶新增的檢視（Q7）。
- 「同一個屬性」的粒度：物件型項目（轉換、事件等）比頂層屬性，不往下比巢狀陣列的每一筆，例如事件的 `effects` 整個陣列算一個屬性。
- 群組名稱、`requires` 不是比對項目：群組屬於客戶的組織，新版改了群組名稱不去改客戶的群組；`requires` 是新版的前置條件，在 §8.2 檢查。
- 主檔的基本欄位只在升級主檔時比；升級一般應用程式時只比它自己的貢獻。
- 主檔模組的「可擴充」（`extensible`）不比（pkg1b 審查 S3）：它不存資料庫，執行期直接讀目前套件，比對模式匯出也取自候選新版，現況永遠等於新版，比了一定一致。
- `config` 的預設值（pkg1b 審查 M1）：只有不可為 null、預設 false 的旗標（`required`、`readOnly`、`defaultToday`、`showInList`、`isFilterable`、`isSortable`）把 false 當缺漏；`fullWidth` 先解析成有效值（省略時多行文字佔滿、其他不佔滿，同前端 `form-layout.ts`），等於型別預設才當缺漏；`defaultValue` 等其他鍵的 false 照比。
- 屬性歸類（pkg1b 審查 M2）：程式裡每個套件 record 不是「整份比對」（`UpgradeItems.AutoCompared`，扣掉不比對清單後所有屬性自動比）就是「手工比對」（`HandCompared`，逐一列出比哪些屬性）；不比對的屬性列在 `NotCompared` 並附理由。§18 的覆蓋率測試照這三份清單雙向檢查。
- 主檔模組的權限不能讀有效值來比：有效值是各來源重算的結果（`MasterGrants`），讀有效值會把別的應用程式授予的、權限頁手動改的（記成 `Manual` 來源，`MasterGrants.SaveAsync`）都算成「客戶改」。只比本應用程式名下的來源記錄，客戶在權限頁的手動調整是另一個來源，升級不碰也不比。

#### 6.2.1 群組的正規化（審查必修 5）

權限類項目（模組權限、欄位例外、選項範圍，以及報表分享、轉移群組、簽核關卡群組這些屬性裡的群組）比對前，B 與 N 先換成客戶群組：

1. 用 `GroupMapJson` 把套件群組代號換成客戶群組 id；N 新增的代號用這次預覽或套用 body 的 `groupMap`。
2. 多個套件群組對到同一個客戶群組時，照開啟的合併規則合成一筆：模組權限動作取聯集、範圍取最寬（同 `MasterGrants.GrantAsync`）；欄位例外取最嚴，隱藏優先於唯讀（同 `AppOpener.RecordGrantsAsync`）；選項範圍取聯集。合併後才比，所以 C 的一筆合併列不會被比出假差異。
3. 對到 `null`（略過）的群組：既有物件上的相關權限項目不列（反正只列出、不能套，列了只是雜訊）。新模組、新物件用到它時，群組段列出這個代號，預設維持略過；管理員改成對應或新建之後，那些權限才隨新物件一起寫（fail closed：不改就不給權限，同開啟）。報表分享、轉移群組裡的略過群組直接從集合拿掉再比。
4. 簽核關卡的群組：比對前先照開啟時的備援規則（`AppApprovalFlowCodec.Substitutions`，`AppOpenPlanner.cs:134`）把略過的群組換成備援，B 與 N 都換，才和 C 一致。
5. 一般模組的權限識別因此是「模組＋客戶群組 id」，不是套件群組代號；畫面顯示客戶群組名稱，後面括號列出它對到的套件群組代號。

### 6.3 分類（T6）

對每個項目的每個屬性，比 B、N、C 三個值：

| B 對 N | B 對 C | C 對 N | 屬性的結果 |
|---|---|---|---|
| 相同 | 相同 | — | 一致（不列） |
| 不同 | 相同 | — | 只有新版改 |
| 相同 | 不同 | — | 只有客戶改 |
| 不同 | 不同 | 相同 | 一致（兩邊改成一樣，不列） |
| 不同 | 不同 | 不同 | 兩邊都改（衝突） |

**多語文字逐語系比**：`I18nText` 屬性的每個語系鍵各自是一個屬性。新版補了 en-US、客戶匯入了 ja，兩者是不同屬性，不衝突，合併後兩語都在。

**項目的分類**由它的屬性決定（Q2）：

- 有任何衝突屬性 → **兩邊都改**，預設不勾，列出原值（B）、新版（N）、目前（C）。
- 沒有衝突、有「只有新版改」的屬性 → **只有新版改**，預設勾；「只有客戶改」的屬性保留客戶的值。
- 只有「只有客戶改」的屬性 → **只有客戶改**，只列出、沒有可勾的東西（套用不會碰它）。

**存在與否**另外分：

| B | N | C | 分類 | 預設 |
|---|---|---|---|---|
| 無 | 有 | 無 | 新版新增 | 勾 |
| 有 | 有 | 無 | 客戶已刪除（Q1） | 不勾 |
| 有 | 無 | 有 | 新版移除：只列出，保留不刪（Q4） | 不能勾 |
| 有 | 無 | 無 | 兩邊都刪（不列） | — |
| 無 | 有 | 有 | 新版新增，但客戶已有同代號的東西（例如共用主檔合併補進來的欄位）：C＝N 不列；不同算兩邊都改 | 不勾 |
| 無 | 無 | 有 | 客戶新增：只算數量，不比對、不動 | — |

- **上次略過**（Q3，pkg1-5）：項目或屬性列在基準的 `SkippedJson`，而且客戶現值仍等於當時記下的舊值（略過之後客戶沒再動它），分類改成「上次略過」，預設不勾、可勾回；顯示當時記下的舊值、這次新版的值。客戶後來動過（現值和記下的舊值不同），這筆略過紀錄作廢，照一般規則分類。
- 「客戶新增」靠**有沒有對照列**判斷，不靠代號字串：設計器後加的欄位匯出時代號是 `f_<id>`，萬一新版剛好也有叫 `f_123` 的欄位，兩者也不會被當成同一個。
- 開啟時排除的欄位（`ExcludedFieldsJson`）在 C 裡沒有，分類寫「開啟時略過」，預設不勾（同客戶已刪除）。
- 欄位被客戶停用：「啟用狀態」是一個屬性，停用就是「只有客戶改」；新版改了它的標籤照樣能套，套完仍是停用。
- **沒有基準**（§4）：B 當成不存在。C、N 都有且不同的項目標「沒有基準」；N 有、C 沒有的也標「沒有基準」；全部預設不勾。N 沒有、C 有的當客戶新增。

### 6.4 無法套用的差異

以下列在預覽、標「無法套用」與原因，不能勾：

- 欄位型別不同（`UpdateFieldHandler` 不允許改型別）。
- 既有欄位改成必填，而模組裡有記錄沒填這個欄位（分流 pkg1-3、Q8）：原因「會影響既有資料：N 筆沒有值，請在設計器手動處理」，附「到設計器」連結。沒有空值的記錄時照一般規則可以勾。
- 既有模組、既有欄位、既有選項的權限修改（Q5）。
- 「會不會影響既有資料」的判斷只寫一份設計器指令分類，pkg1 與 mcp3（AI 改已有資料的模組）共用（2026-11-19 分流技術決定 17、mcp3-3），不在 pkg1 另寫一套。
- 模組種類、擴充宿主不同。
- 欄位換了區塊或排序、選項排序、區塊排序：不比對（T7）。新加的欄位放在新版裡它前一個欄位的後面，前一個不存在就放區塊最後；新加的選項放最後。
- 現況匯出時表達不了的項目（§6.1）：標「無法比對」，原因帶匯出的 warning。
- 既有欄位的參照對象（`config.refTarget`）或關聯方式（`config.relation`）不同（pkg1b 審查 S2）：`FieldConfig` 規定建立後不能改、`UpdateField` 不允許，比照型別標無法套用，原因代碼 `referenceChanged`。

### 6.5 相依（T8）

有些項目要靠別的項目才成立，例如新版新增的報表用到一個新欄位、新選項；新轉移要用到新狀態；新欄位的公式引用另一個新欄位。

- 預覽替每個項目算出 `dependsOn`（項目識別清單），只列 C 裡還不存在的項目。
- 引用的判斷（`UpgradeItems.References`）：項目內容裡出現的字串，限定名（`模組.代號`）或同模組的裸代號都算；字串裡的 `{代號}`（公式、樣板）逐個拆出；轉移另帶起訖狀態的限定名，所以新轉移連得上新狀態（pkg1b 審查 S1）。寬鬆時最多多連勾幾項，漏掉才危險。
- 畫面勾一個項目時自動一起勾它依賴的項目（並提示「一起套用：…」）；取消依賴項目時，依賴它的也一起取消。
- 後端再驗一次：勾了的項目依賴沒勾、或「客戶已刪除」且沒勾回的項目 → 400，列出缺的項目。驗證不只做在前端（鐵則 5）。
- 開啟時排除、被新版移進新區塊的欄位另列成可勾項目（§8.4），被檢視、規則、公式、模組標題引用時照這裡的規則：沒勾回 400，不會套用到一半才因找不到欄位失敗（複核 N1）。
- pkg1d 補的相依規則（物件依賴自己所在的新模組、需簽核轉移依賴新流程、流程依賴目標與退回狀態、列印範本的明細迴圈、主檔符號換算、事件與轉換與起始狀態依賴新狀態）見 §9.6.1（T43）。

## 7. 新版的來源與版號

### 7.1 候選新版（Q9）

| 應用程式的來源 | 候選新版 |
|---|---|
| 內建（`App.Source = builtIn`） | 目錄裡同 id 的內建套件 |
| 匯入（`imported`） | `Dynamic_AppPackage` 裡同 id 的那份 |
| 共用主檔 | 內建與匯入兩份裡版號較大的那份，同版號取匯入的（主檔匯入是合併，內建與匯入本來就混用，共用主檔設計 §9） |

- **候選來源集中在 `AppPackageSource`**（審查建議 2，T19），但「開啟用哪一份」和「升級候選是哪一份」對主檔分開（pkg1b 審查 S17）：
  - **開啟、自動開啟主檔、再匯入主檔的合併底稿**（`FindAsync`；套件清單與已知主檔 `ListAsync` 同規則）：主檔有匯入的合併副本就用它，不比版號。合併副本保留當時的 manifest（`MasterMerger.MergeDefinition`），內建之後出了版號較大的新版時，若改用內建版，客戶之前「再匯入主檔」補進來的欄位會在自動開啟時不見，再匯入時也會以內建版為底稿合併、把舊副本覆寫掉，等於資料遺失。
  - **升級候選**（`CandidateForAsync`，升級預覽、`upgrade` 提示欄位、預覽的 `masters` 段共用）：已開啟的主檔取內建與匯入兩份裡版號較大的，同版號取匯入的。只有這裡比版號，合併副本才不會永遠遮住內建新版；用內建新版升級時客戶的欄位由三方比對與下一點的副本改寫保住。
- 主檔用內建新版升級後，`Dynamic_AppPackage` 裡的合併副本同步改寫：以內建新版為底、把副本當成匯入的再跑一次 `MergeDefinition`，manifest 用新版的。這樣主檔日後被刪除、再自動開啟時，開到的是新版加上客戶當初匯入補進來的欄位，不會退回舊版。
- 一般應用程式不跨來源：內建開的只能用內建的新版更新，匯入的只能用匯入的。這是「來源標記」的用途：一份外面拿到、自稱 `crm-sales` 的檔案不能拿來更新內建 CRM（現在匯入同 id 本來就 409）。
- 不新增格式欄位（T10）：`manifest.version` 早就是必填（套件設計 §4.3），來源在開啟時記在 `App.Source`。`manifest.vendor` 只顯示；新版的 vendor 和基準不同時，預覽加一行提醒。

### 7.2 版號（T9）

- `manifest.version` 從「只是資訊」改成**升級的判斷依據**：照語意化版本比大小（三段數字，套件設計 §4.3 的格式）。
- 有新版：候選新版的版號大於 `App.PackageVersion`。
- 版號相同：「已是最新」，不能預覽。內容不同但版號沒升，算套件作者的錯，`.claude/rules/app-packages.md` 本來就要求改內容要升版；內建套件由 `AppCatalogChecks` 擋不了（目錄沒有舊版可比），靠 U1 與審查。
- 版號較小：不支援降版，預覽回 409「新版的版號比目前的小」。
- 套用成功後 `App.PackageVersion`、`App.FormatVersion` 換成新版的。匯出的 `manifest.version` 因此會是新版號（匯出本來就沿用這個值，套件設計決策 15 的代價說明照舊成立）。

### 7.3 匯入套件的新版（Q9）

`ImportAppPackage` 對已匯入過的一般應用程式 id：

- 版號較大：**取代** `Dynamic_AppPackage` 那一列的原文與版號，回 200「已匯入新版，已開啟的應用程式可以到更新頁套用」。舊原文不留：已開啟的應用程式有自己的基準，還沒開啟的直接開新版就好。
- 版號相同或較小：維持 409「套件代碼已存在」，訊息補上目前的版號。
- 與內建同 id：維持 409（不跨來源）。
- 共用主檔照舊走合併（共用主檔設計 §9），不受這條影響。

## 8. API

路由沿用 `AppsController`（`/api/v3/dynamic/apps/...`）。

### 8.1 預覽

`POST apps/{key}/upgrade/preview`，body `UpgradeBody { groupMap?, moduleKeys? }`（形狀同 `OpenAppBody` 的這兩項；預覽第一次可以不帶）。不寫入任何東西。

回應 `UpgradePreview`：

| 屬性 | 說明 |
|---|---|
| `app`、`fromVersion`、`toVersion` | 應用程式與版號 |
| `hasBaseline` | 沒有基準時 false，畫面顯示說明 |
| `token` | 預覽時三份輸入的雜湊（§8.3） |
| `canApply`、`blockers` | 不能套用的原因：應用程式已關閉（Q6）、新版缺的前置條件、驗證錯誤 |
| `groups` | 要決定對應的群組代號：新版多出來的、對照已失效的、開啟時略過而新物件用得到的；附目前選擇（body 帶的 `groupMap`，沒帶時用建議：新代號同開啟的建議，略過過的建議維持略過）。已經對應好、還有效的代號不在這裡，不能改（T26） |
| `keyConflicts` | 新版新增模組的預設 key 和現有模組衝突，同開啟的 409 列法 |
| `items` | 差異項目（§8.4），「一致」的不列 |
| `counts` | 各分類數量，含「客戶新增」的數量 |
| `masters` | 一起更新的共用主檔，每份有 `id`、`name`、`fromVersion`、`toVersion`、`hasBaseline`、`groups`（同上，主檔自己的群組代號）、`items`、`counts`（Q10） |
| `warnings` | 例如 vendor 不同、新版帶未安裝語系的文字（同開啟預覽，語系包設計 U6） |
| `name`、`vendor` | 應用程式名稱（多語）與新版的 `manifest.vendor`，頁首顯示用 |

以下是 pkg1b 定下、pkg1c 要依賴的契約細節（pkg1b 審查 M3 回填）：

- **`blockers`** 每筆 `{ code, detail }`，`code` 由前端翻譯（`apps.upgrade.blocker.<code>`），`detail` 是補充（應用程式 id、驗證訊息；主檔的前面加主檔 id）。代碼：`closed`（應用程式已關閉，Q6）、`exportFailed`（現況匯出失敗）、`invalidPackage`（新版沒通過驗證或政策上限）、`requiresUpdate`（需要的模組要等別的應用程式先更新，`detail` 是那個應用程式 id）、`requiresApp`（需要的應用程式、主檔或實體沒開啟）、`secondBatch`（第二批項目有差異，pkg1d 之前整個擋下，§15）、`masterPending`（用到的共用主檔有新版，`detail` 是主檔 id，pkg1d 之前整個擋下）、`hostTaken`（新模組要擴充的宿主已被其他模組佔用，`detail` 是新模組代號，§8.2 第 3 點）。`secondBatch`、`masterPending` 在 pkg1d2 合併時刪除（§9.6.3）。
- **`groups[].reason`**：`new`（新版多的代號）、`stale`（對到的群組已刪除）、`skipped`（開啟時略過）。`choice` 是 `{ mode, groupId }`，`mode` 為 `map`、`create`、`skip`。
- **409 有四種**，都回訊息文字：版號相同「已是最新」、目錄裡找不到這個應用程式的候選「沒有可用的新版」、候選版號較小「新版的版號比目前的小，不支援降版」、直接對共用主檔的 key 預覽回 `MasterManaged`（與開啟、關閉主檔同一句；主檔的新版從使用它的應用程式更新頁看，Q10，pkg1b 審查 S8）。應用程式本身不是新版、但用到的共用主檔有新版時照常回預覽（只含 `masters`）。降版目前排在主檔候選之前判斷（pkg1b 審查 S7，延到 pkg1c 決定）。

### 8.2 前置檢查

照開啟的前置檢查（套件設計 §6.2）挑適用的：

1. 新版通過套件驗證（四層）與政策上限（`PackageLimitReader`；上限是對整份新版檢查，同開啟）。
2. 新版的 `requires` 滿足：需要的應用程式、模組、主檔都已開啟；需要的是別的應用程式新版才有的模組時，`blockers` 寫「請先更新 ○○」。不自動連帶更新（同套件設計決策 5）。
3. 新版新增的模組 key 不衝突；擴充宿主沒被佔用。
4. 應用程式是 `Open`（Q6）。

### 8.3 套用

`POST apps/{key}/upgrade`，body：`{ token, items: [項目識別], groupMap, moduleKeys, masters: { 主檔 id: [項目識別] } }`。

- `token` 和現在重算的不同 → 409「內容已變更，請重新預覽」（T11）。雜湊涵蓋這個應用程式**以及每一份列在 `masters` 的共用主檔**各自的三份輸入：基準原文、新版原文、現況比對模式匯出的正規化結果，再加上群組對應。預覽和套用之間有人改了設計、匯入了新版、或從另一個應用程式的更新頁先套用了同一份主檔，都會換掉雜湊。
- token 的重算在套用的交易內做，排在任何寫入之前；PostgreSQL 的交易第一個陳述式就取全庫寫入鎖（`PostgresWriteLockInterceptor`），所以重算時已經拿到鎖，兩個管理員同時套用不會都通過比對。SQLite 由寫入序列化保證同樣的效果。
- `items` 裡有「無法套用」「只有客戶改」「新版移除」的識別 → 400。
- 相依沒滿足 → 400（§6.5）。
- 成功回 200 與 `AppResponse`（同開啟），附 `warnings`。

pkg1c 實作補記（2026-11-22）：

- 預覽的 `canApply` 為 false 時套用回 409，內容附這次的預覽（前端照它重新顯示）；token 不符同樣 409。兩者都在勾選驗證之前判斷。
- 勾選驗證的 400 以 `items.<項目識別>` 為鍵：不在這次清單、不能套用、缺的相依（訊息列出缺的項目識別）。
- 設計器指令失敗時，既有物件的修改、規則組、檢視、報表的錯誤鍵前面加項目識別（`<項目識別>.<原本的鍵>`），409、404 的訊息前面加項目識別；新模組與新欄位的建立失敗沿用實例化的鍵（`<模組代號>.<欄位代號>.…`、`contributions.<模組代號>.<欄位代號>.…`）。畫面直接顯示訊息。
- `masters` 先不收：共用主檔有新版時整個套用擋 `masterPending`（主檔一起更新留 pkg1d，§15），所以 pkg1c 的 token 只涵蓋應用程式自己。
- 409 帶 `code` 讓畫面分辨（審查 M5）：token 不符是 `upgradeStale`，畫面提示「內容已變更」並重新預覽；`canApply` 為 false 是 `upgradeBlocked`，內容附預覽，畫面用它重畫、列出 `blockers`；已是最新、沒有新版、降版（預覽也回同樣的 409）是 `upgradeUnavailable`，畫面重新預覽、收起舊清單；沒有 `code` 的 409 是設計器指令擋下（訊息前面有項目識別），畫面只顯示訊息、不重新預覽。400 的 `errors` 逐鍵列出，鍵裡與訊息裡的項目識別換成項目名稱。重新預覽失敗（例如已是最新）時清掉舊清單與套用鈕，只顯示原因。
- 既有報表的修改與分享不經報表指令（兩者只讓擁有者改），在套用裡直接寫，定義照樣驗證，擁有者不變（審查 M3）。
- 稽核明細的單項本身超過一筆的上限時，舊值、新值改記 `{ length, sha256 }` 並標 `truncated`（審查 S1）；新模組、新欄位、新選項附帶的權限也逐筆記（`old` 為 null，審查 S2）。

### 8.4 項目的形狀

```json
{
  "id": "field:lead.source",
  "section": "fields",
  "module": "lead",
  "label": { "zh-TW": "來源", "en-US": "Source" },
  "category": "both",
  "defaultSelected": false,
  "applicable": true,
  "reason": null,
  "dependsOn": [],
  "properties": [
    { "name": "label", "locale": "zh-TW", "base": "線索來源", "new": "來源", "current": "名單來源", "result": "both" },
    { "name": "label", "locale": "th", "base": "ที่มา", "new": "แหล่งที่มา", "current": "ที่มา", "result": "newOnly" }
  ]
}
```

- `reason`：不能勾或要說明時的**原因代碼**，由前端翻譯（`apps.upgrade.reason.<code>`），能照一般規則勾時是 null。代碼：`customerOnly`（只有客戶改）、`removedInNew`（新版移除）、`typeChanged`（欄位型別不同）、`kindChanged`（模組種類或擴充宿主不同）、`referenceChanged`（參照對象或關聯方式不同）、`existingPermission`（既有物件的權限修改，Q5）、`notYetSupported`（第二批項目，pkg1d 之前不能套用，§15）、`affectsData`（既有欄位這次會改成必填、有記錄沒填值，§6.4）、`unmatched`（現況有對照列、比對模式卻表達不了，§6.1）。pkg1d 新增的代碼與資訊型的 `impacts` 見 §9.6.4。§6.4 寫的原因文字是畫面上翻譯後的樣子，不在 API 裡。
- `affectedRecords`：只在 `reason` 是 `affectsData` 時有值，是沒填值的記錄數；只有「必填」這次真的會寫入（不是客戶改成非必填而保留）時才判斷（審查 M4）。
- `dependsOn`：引用到的「現況還沒有、這次列出」的項目。引用的對象是新區塊、新模組底下的項目時（它們不另列），指向列出的那個區塊或模組；模組項目看標題欄位與標題樣板，規則看 target 的 `field:`／`block:` 與條件值的 `opt_` 去掉前綴後的代號（審查 M2）。開啟時排除、被新版移進新區塊的欄位，套用新區塊時預設不建（審查 S3），所以另列成 `excludedAtOpen` 項目、預設不勾，`dependsOn` 帶它所在的新區塊；引用它的項目依賴它本身，依賴它的項目（連同再依賴這些的）也預設不勾，預設勾選才能直接套用。新區塊、新模組底下不另列的項目引用別的新項目時，算在列出的上層頭上（例如同一個新區塊裡的公式引用這類欄位，新區塊就依賴它）（複核 N1）。
- `attachedPermissions`：新模組、新欄位、新選項、新貢獻附帶的權限（Q12），以及新轉移可推進的群組（pkg1d，T57），每條 `{ groupId, groupName, effect, grants, scope }`（`scope` 只有模組權限有，是資料範圍）；選了「建立新群組」的代號，`groupId` 是**負數暫代 id**（這次預覽裡將新建的群組，同一次預覽內每個代號固定一個），`groupName` 是套件裡的群組名稱。負數 id 只給畫面顯示，套用時不得送回、也不能拿去查群組；`effect` 是動作或限制（`hidden`、`readOnly`、`visible`、`read`、`edit`…，含資料範圍），`grants` 為 true 表示給權類。和 `defaultSelected` 一樣只在後端算，畫面的「給權」標示照它顯示。
- `category`：`newOnly`、`customerOnly`、`both`、`added`、`customerDeleted`、`removedInNew`、`excludedAtOpen`、`skippedBefore`、`noBaseline`、`unmatched`。
- `label` 給畫面顯示，取新版的值，沒有新版（新版移除）取現況的。
- 值一律原樣回（字串、數字、物件），由前端格式化；`config` 的鍵用欄位設定畫面的名稱顯示（i18n 鍵 `apps.upgrade.prop.<name>`）。

### 8.5 有新版的提示

`GET apps/packages` 的每個項目加 `upgrade: { toVersion: string | null, masters: [{ id, toVersion }] } | null`：應用程式已開啟或已關閉，且它自己或它用到的共用主檔有候選新版時有值；`toVersion` 是應用程式自己的新版號，只有主檔有新版時為 `null`、`masters` 列出主檔（Q10 的「共用主檔有新版」）。`GET apps/{key}` 同樣加。不另開查詢。

## 9. 套用

### 9.1 順序與交易（T12）

整個套用是一個 `ITransactionalRequest`，任何一步失敗整批回滾；外層 `PackageTextScope`，只要求繁中。順序照開啟的順序，讓依賴的東西先建好：

0. 重算 token 並比對（§8.3）。
1. 共用主檔的新群組：`create` 的建立、`map` 的記下。
2. 共用主檔的項目（下面 4–8 步同樣的順序，先主檔、後使用者應用程式）。
3. 應用程式的新群組。
4. 新模組：用 `TemplateInstantiator` 只實例化勾選的新模組（外部引用指向既有模組），依 `ActivationOrder` 啟用，寫 `AppModule` 與對照列。
5. 既有模組的區塊、欄位、選項：新增的寫對照列（`AppBlock`、`AppField`、`AppOption`），沿用開啟的代號規則。
6. 規則組、共用檢視。
7. 權限，只處理新模組與新物件附帶的權限（Q5、Q12；給權類記在應用程式名下、關閉時收回），分兩種（審查必修 1）：
   - **一般模組**：新模組在第 4 步實例化時就帶權限（同開啟）；既有模組上的新欄位、新選項的欄位例外、選項範圍，從現有權限列出發加上去，再呼叫一次 `SaveModulePermissions`（整份取代，不能分次）。既有的權限列一筆都不改。同一個客戶群組只會有一筆（§6.2.1 已合併），不會被 `SaveModulePermissionsHandler` 的「設定重複」擋下。
   - **主檔模組與貢獻**（新貢獻、新貢獻欄位）：不用 `SaveModulePermissions`（它會把差異記成 `Manual` 來源，`MasterGrants.SaveAsync`；手動來源永遠計入，應用程式關閉後寫入權限收不回來）。改成 `MasterGrants.GrantAsync(GrantSource.Master 或 App, appId, …)` 寫本應用程式名下的來源記錄；新增的貢獻欄位標「限定可見」並補本應用程式的 `FieldGrant` 列（同 `AppOpener.RecordGrantsAsync`）；最後重算受影響模組的有效值（`MasterLifecycle.RecomputeAsync`）。
   - 合併規則照 §6.2.1：模組權限動作取聯集、範圍取最寬；欄位例外取最嚴；選項範圍取聯集。
8. 報表、狀態機、轉換、列印範本、分錄、事件、檢查、簽核流程、任務規則（套件設計 §6.2 第 7 步之後的順序，`AppFlowInstaller` 的順序；pkg1d 的細化見 §9.6.1，貢獻改在第 5 步和欄位一起建）。
9. 整合：改已安裝的項目、登記 `ItemsJson`、換宣告、補列（§9.6.2 整合）；這一步不調和。
10. `App` 的名稱、圖示、`PackageVersion`、`FormatVersion`，`TouchRowVersion`；基準整列換成新版（§9.2）；升級的是主檔時改寫合併副本（§7.1）；`CommitAsync`。
11. 調和（T52，設計審查 D9）：在同一個交易內、第 10 步最後一次 `CommitAsync` 之後，才呼叫 `ReconcileAsync(only: …)`，只調和這次動到的整合；主檔與應用程式都套完後才調和，之後不再修改任何已追蹤的實體。調和失敗只進 warnings，不讓套用失敗（同開啟）。理由：`EnsureInSavepointAsync` 要開 savepoint，`EfWorkSavepoints` 在交易外直接丟例外，所以不能放進 `AfterCommitActions`；savepoint 回滾會清掉 change tracker，調和若排在第 10 步之前，一失敗回滾，第 10 步對已追蹤實體的修改就不會寫進資料庫，結果是套用成功、內容換新，版號與基準卻沒換，下次預覽冒出一堆假差異（開啟也是同樣的做法，`OpenApp.cs:194-196`）。

每一步呼叫既有的設計器指令，所以現有驗證照跑（公式能不能解析、規則條件、報表定義、簽核流程定義）。失敗時回應帶失敗的項目識別與原因。

**失敗處理**（審查建議 12）：套用 handler 是外層交易，內層指令經 `TransactionBehavior` 時是巢狀、不另開交易，內層回失敗**不會自己回滾**。所以套用 handler 遇到第一個失敗的結果就停、回失敗，由外層整批回滾；不嘗試「略過失敗的項目繼續套」。PostgreSQL 交易內遇到資料庫錯誤後不能再發 SQL（`.claude/rules/backend.md`），這也是不能繼續的原因。

### 9.2 套用後的基準（Q3，使用者裁決 2026-11-21）

基準原文整份換成新版原文，**不論哪些項目有勾**。`GroupMapJson` 補上這次新對應的群組；`ExcludedFieldsJson` 保留（開啟時略過的欄位仍是略過）。

`SkippedJson` 換成這次的略過清單：這次列出、`applicable` 為 true、卻沒勾的每個項目（含它的可套用屬性），記項目識別、屬性與語系、當時客戶的值、當時新版的值。上一次的略過紀錄，這次又沒勾的照樣帶過去（舊值不變）；勾了的、或客戶已改過的就拿掉。

結果：沒勾的項目下次升級**還會列出**，標「上次略過」、預設不勾、可以勾回（§6.3）。如果沒有這份清單，因為基準已經換成新版，沒套的修改下次會變成「只有客戶改」、沒加的新項目會變成「客戶已刪除」，管理員分不出是自己略過的還是自己改的。

仍只有 pkg1a 一組 migration：`SkippedJson` 是同一張表的一欄。

### 9.3 稽核

動作代碼 `app.upgrade`，目標是應用程式（`AuditTargets.App`），摘要「1.3.0 → 1.4.0，套用 12 項，略過 3 項」；各設計器指令自己的稽核照記（同開啟）。摘要之外逐項記「舊值 → 新值」（分流 pkg1-8）：每個套用的項目一筆 `{項目識別, 屬性, 語系, 舊值, 新值}`，舊值取套用前的現況 C。內容超過 `AuditLogEntry.SummaryMax`（16,000 字）時拆成多筆 `app.upgrade.items` 稽核（同一個 `RequestId`，摘要標「第 k／n 筆」），不截斷（T25）。各設計器指令自己的稽核仍照記，但管理員要改回時看 `app.upgrade` 這幾筆就夠。摘要是寫進資料的系統文字，用系統預設語系（使用者 2026-11-20 裁決），經 `IMessageCatalog` 取文案，訊息鍵集中在 `AppMessages`。

### 9.5 pkg1c 實作補記（2026-11-22）

- **新欄位的權限**（§9.1 第 7 步一般模組）：沒有呼叫 `SaveModulePermissions`，改用 `IPermissionRepository.ReplaceModuleRowsAsync` 以現有權限列為底、只加新欄位的欄位例外與新選項的選項範圍，既有列一筆都不改。理由：這一步只加列，不必組整份模組權限的請求；效果同「從現有權限列出發加上去」，同一個客戶群組多個套件群組時欄位例外取最嚴。新模組的權限照開啟，在實例化時帶入。
- **新欄位對應的區塊不在現況**（客戶刪了或換了那個區塊）：欄位放進模組的第一個區塊；新版的新區塊則先建區塊再放欄位。欄位位置放在新版裡它前一個欄位之後，前一個不在同一區塊就放區塊最後（T7）。
- **新欄位的建立順序**：既有模組的新欄位以每個區塊一份「貢獻」交給 `TemplateInstantiator`。貢獻欄位改成**跨貢獻**排序：所有貢獻的一般欄位先建，公式欄位依彼此的引用排在後面（以「模組代號.欄位代號」比）。之前只在單一貢獻內排序，新欄位分在不同區塊、公式引用另一個區塊的新欄位時套用回 500。開啟共用主檔貢獻用同一段程式，順序規則一樣適用。
- **共用檢視保留客戶的條件**：檢視合併後保留的是比對模式匯出的條件（代號寫法）。條件用了客戶自己加的下拉欄位（`f_<id>`，新版沒有這個欄位）時，`IdMap` 不認得它是下拉欄位，選項值 `opt_o_<id>` 不會換回 `opt_<id>`；檢視驗證會擋下、整個套用失敗（不會寫出壞資料）。套用前先把這類欄位的選項值換回 id。規則組整組換成新版，條件只引用套件的欄位，沒有這個問題；報表定義以名稱查欄位與選項，客戶的代號查得到。
- **稽核分筆**：摘要那筆放得下逐項明細時直接放 `items`；放不下時摘要記 `itemParts`，另寫 n 筆 `app.upgrade.items`，每筆 `{ part, parts, items }`。
- **已知限制**：新版套件裡設計器才擋得下的錯誤（例如公式欄位的 `resultType` 寫了不支援的值）通過預覽，套用時才失敗、整批回滾，回應帶失敗的項目識別。根因在套件驗證沒有逐項比照設計器的欄位驗證，另開票處理。

#### 9.6.1 共同做法

- **比對的分類不改，相依規則補強**（T43，主控已定，可推翻；設計審查 D4、S11、S15）：識別、屬性、分類照 pkg1b 已上線的比對引擎（`UpgradeItems.Extract`、§6.2 的表）。物件型項目仍比頂層屬性：事件的 `effects`、轉換的 `header`／`lines`、任務規則的 `tasks`、列印範本的 `body` 各算一個屬性；唯一的例外是簽核流程的 `stages` 依 Q27 拆出 `approvers` 屬性（§9.6.2 簽核流程，T59）。現有的 `UpgradeItems.References` 抓不到下列引用，§6.5 的相依驗證因此有缺口。第 1–4、6 點在 pkg1d1a 補上（純函式，含 pkg1c 已上線的新報表）；第 5 點在 pkg1d2，和主檔套用一起做（T37；pkg1d1a、pkg1d1b 期間主檔仍被 `masterPending` 擋下，用不到，複核 R8）：
  1. Coded 類物件（轉換、事件、檢查、列印範本、任務規則、簽核流程）與報表，依賴**自己所在的新模組**。`References` 對模組類目標有 `item.Module != target.Module` 的排除（`UpgradeItems.cs:409`），這幾類的 `Module` 就是所屬模組，結果新模組上的新流程、新列印範本不依賴那個新模組，管理員取消勾模組時前端不會連帶取消，套用到一半才 400。pkg1c 已上線的新報表（`Module` 等於 `mainModule`）是同一個根因，一起修。
  2. 需簽核的轉移依賴 N 裡目標為它 `to` 的簽核流程（同模組）。轉移的 Refs 只有模組與起訖狀態，依賴要從流程的（模組、`to`）反查。只在**現況 C 的目標狀態上沒有流程**時才加（複核 R1）：客戶已經有流程時，第一趟就能帶需簽核，不必等新流程；這時若加了相依，新流程又被 `priorityTaken` 擋下，轉移會跟著變成套不了。被依賴的流程可以是新增的，也可以是既有、未用過、這次把 `to` 改到這個狀態的流程（修改項目）；後者是 §6.5「只列 C 裡還不存在的項目」唯一的例外，不列的話管理員只勾轉移、不勾流程修改時，第二趟會報 `NoFlow`。
  3. 簽核流程依賴 `state:<模組>.<to>` 與 `state:<模組>.<rejectTo>`。流程的 Refs 目前只有裸選項代號，選項已存在、狀態是這次新加的時候對不上。
  4. 列印範本依賴 `{{#each 明細模組}}` 的模組，以及迴圈裡的明細欄位（限定名用明細模組，不是範本所在的模組）。現在的 `Placeholder` 規則吃不到 `#each`。
  5. 應用程式項目引用主檔欄位時寫主檔符號（`partner/partner.fax`），主檔項目的識別卻是 `field:partner.fax`。`References` 先把主檔符號換成 `master:<主檔 id>/field:<模組>.<欄位>` 再比（T37）。**pkg1d2 做**。
  6. 事件的 `trigger.from`／`trigger.to`、轉換的 `sourceStates` 依賴 `state:<來源模組>.<選項>`；`workflow:<模組>` 依賴 `state:<模組>.<initial>`（複核 N1）。三個設計器驗證都要求引用的狀態已在狀態機裡（`EventValidator.cs:98-99`、`ConversionValidator.cs:57`、`SaveWorkflowHandler.cs:53`），這幾類的 Refs 卻只有裸選項代號（`cancelled`），狀態項目的識別是 `state:<模組>.cancelled`，`References` 比的是 `<模組>.cancelled`，對不上；結果只依賴到選項、依賴不到狀態，管理員勾了事件與選項、沒勾狀態時套到一半 400。做法同第 3 點：Extract 時把限定名 `<模組>.<選項>` 加進 Refs。狀態機整份是新的（狀態隨它 `Subsumed`、不另列）時，相依自然滿足。

  規則寧寬勿漏：寬鬆最多多連勾幾項，漏掉就會套到一半失敗（§6.5）。
  - **新模組與它的新流程互相依賴**（複核 N5）：新模組底下的狀態機與轉移隨模組 `Subsumed`、不另列，隱藏子項目的引用算在列出的上層頭上（`AppUpgradePreviewer.cs:347-357`）。第 2 點上線後，新模組 `complaint` 底下需簽核的轉移讓模組依賴目標上的新流程，流程又因第 1 點依賴模組，兩者互相依賴：一起勾、一起取消。這是預期行為，不是 bug。前端 `toggleItem` 有 `on === next.has(current)` 防線（`frontend/src/presentation/dynamic/upgrade/upgrade-view.ts:94`），不會無限遞迴；後端驗證是集合比對，也沒有問題。前端補一格 vitest（S5）。
- **修改＝以現況為底、換掉要寫的屬性，再整份存**（T29，主控已定，可推翻）：各 `Update*` 指令都收整份定義，所以照 pkg1c 的 `AppUpgrader.Merge`，以比對模式匯出的現況（C）為底，把「只有新版改」與勾選後的衝突屬性換成新版（N），再把代號換成 id（`AppEffectsCodec`、`AppPrintCodec`、`AppTaskRuleCodec`、`AppApprovalFlowCodec` 的 `ToInput`，以及轉換的 `AppFlowInstaller.ConversionInputOf`；後者目前是 private，改 internal 讓修改路徑共用，審查 S9），以 Key 送 `Update*`。客戶改的屬性保留，例如客戶停用了事件（`active` 是只有客戶改），新版改了它的效果，套用後效果換新、仍是停用。
- **群組代號先換成 id 再合併**（T44，主控已定，可推翻；審查 D3）：C 是比對模式匯出，群組代號是客戶群組的 Key（`AppExporter.GroupCode`）；N 的群組代號是套件代號，要經群組對應才換得成 id。兩套代號只要有一個字串相同、指向的群組不同，在 JSON 層合併後用同一份代號表 `ToInput` 就會解析錯。例子：套件的 `sales` 對到客戶群組 7（Key 是 `crm-sales`），客戶另有一個 Key 為 `sales` 的群組 9；合併後的簽核人或推轉移的群組被換成群組 9，屬於權限錯誤。所以合併前 C 經群組 Key、N 經 `GroupMapJson`＋這次的 `groupMap` 各自換成客戶群組 id，合併在 id 層做，再交給 codec（`ToInput` 改收已解析的群組 id，或收兩份「代號 → id」表，實作者定）。狀態機更直接：以資料庫現有的 `Workflow`（本來就是 id）為底，只把勾選的新版狀態與轉移換成 id 加進去或改掉。
- **新增的物件**（T30，主控已定，可推翻）：組一份只含勾選新物件的子套件（`Reports` 設成 `[]`，報表仍走 pkg1c 的 `SaveReportsAsync`），交給 `AppFlowInstaller` 的逐階段入口（T45）與 `InstallTaskRulesAsync`。代號對照用套用當下的現況（同 pkg1c 的 `TemplateInstantiator.MapFor`；`IdMap` 的 `Fields`、`Options`、`Modules`、`Blocks` 轉成 `AppFlowInstaller` 要的 `TemplateIdMap`，`ModuleKeys` 併入主檔符號與外部模組）。新模組底下的狀態機、分錄（`Parent` 是模組，預覽不另列）隨新模組一起裝，不再擋 `secondBatch`：`Subsumed` 的擋法照 `IsSecondBatch` 判斷，狀態機在 pkg1d1a 合併時放行，分錄在 pkg1d1b 合併時放行（§9.6.7）。
- **`AppFlowInstaller` 拆成逐階段入口，加嚴格模式**（T45，主控已定，可推翻；審查 D2、S8）：`InstallAsync` 是單一入口，從狀態機兩趟一路跑到列印範本，中間沒有切點；升級卻要讓新物件和既有物件的修改交錯：新簽核流程的目標是既有狀態機上這次新加的狀態，要等那份狀態機存好；既有轉移改成需簽核，要等新流程建好；既有事件改成沖銷新分錄，要等分錄建好。所以拆成 internal 的逐階段入口（狀態機第一趟、分錄、事件、檢查、簽核流程、狀態機第二趟、轉換、列印範本），開啟照舊依序全部呼叫，升級照 T31 的順序在每個階段之間插入修改。嚴格模式以參數傳進各階段：開啟時「引用被排除的欄位，已略過並警告」的地方，升級改回 400 並帶項目識別。T43 補齊相依後，走到這裡就是程式錯，嚴格模式是最後一道防線，不能默默少裝一項。範圍只限這類「引用找不到」：`TransitionSkipped`（新轉移的群組全部對到略過、整條不建）照舊只給 warning，那是 fail closed 的正常結果。
- **預覽先跑設計器的守衛**（T32，主控已定，可推翻）：套用時才被擋會讓整批回滾，管理員只看到一行錯誤。所以凡是設計器指令會擋的情況（簽核中、簽核鎖定狀態有記錄、分錄已有記錄、檢查回填超過上限、被用過的流程改目標、優先序重複、狀態機整份驗證不過），預覽用**同一份判斷**先算，把該項標成無法套用並給原因代碼（§9.6.4）。守衛的判斷抽成可唯讀呼叫的函式，設計器入口與預覽共用，不在 pkg1 另寫一套（同 T27 的做法）。這些守衛在設計器擋下時，有的回 409（`PendingApprovalGuard`、`LockedDataGuard`、`ledgerLocked`、`backfillLimit`），有的回 400（`CheckRetargetAsync`、`PriorityTakenAsync`、狀態機的整份驗證），本設計統稱「設計器指令會擋」（審查 S17）。
- **預覽守衛的判斷基準與限制**（T46，主控已定，可推翻；審查 D5、S6）：
  1. 逐項判斷：守衛收的是整份候選物件，例如 `RejectWorkflowChangeAsync`、`RejectUnlockAsync` 收整份候選 `Workflow`、只回一個結果，看不出是哪一項造成的。預覽對每一項以「現況加上這一項、再加上它 `dependsOn` 的遞移閉包」組成候選（T58），跑同一份守衛，結果歸給這一項。管理員勾了多項、各自都可以、合起來才違規的情況，由套用時的守衛兜底，整批回滾（已知限制，§22.2）：
     - 409（`PendingApprovalGuard`、`LockedDataGuard` 類）：狀態機一個模組一趟只存一次（T29），失敗時「正在套用的項目」是那個模組這一趟包含的所有項目，訊息前綴寫這份清單（複核 R3）。
     - 400（`workflowInvalid` 類，例如兩條轉移各自合法、合起來違反「進入鎖定狀態一律要簽」）：同樣到套用才失敗，前綴同上。
  2. 一般唯讀狀態的解鎖是**升級專用規則**：`LockedDataGuard` 只看簽核鎖定狀態（`ApprovalTopology.LockedStates`），設計器隨時可以把一般 `ReadOnly` 狀態改成可改。升級把「唯讀改成可改、有記錄停在那裡」也標 `unlocksRecords`（Q14），比設計器嚴（顧問分流 Q14：可逆、照 pkg1-3）。這條在預覽另寫，不是共用的設計器守衛；§18 的「設計器照樣擋」防回歸測試對它不適用。
  3. `CheckIndexer.PrepareAsync` 會寫資料（直接把欄位設成可篩選、回填索引，`CheckIndexer.cs:52`），不能在預覽呼叫。拆成純判斷（哪些欄位要開可篩選、要回填幾筆、會不會超過 `check.maxBackfillRecords`）與寫入兩段，預覽只呼叫前者。`PriorityTakenAsync` 目前是 private，改 internal 或抽出；`CheckRetargetAsync` 已是 public。
  4. 成本：`LockedDataGuard` 每次讀整個模組的記錄；預覽逐項判斷時按模組快取讀到的記錄與狀態，同一次預覽只讀一次。
  5. 預覽沒涵蓋、套用時才失敗的：`CheckIndexer` 回填時遇到加總欄位精度不符，套用時回 409（`NotExactMessage`）；預覽不試算，列為已知限制（§22.2）。
- **狀態機的整份驗證**（T47，主控已定，可推翻；顧問分流 L4、審查 S7）：`SaveWorkflow` 除了兩個 409 守衛，還有回 400 的驗證：轉移重複、群組不存在、需簽核的拓撲（`ApprovalConstraints.Validate`，例如「進入簽核鎖定狀態一律要簽」）、事件把狀態推進到需簽核轉移（`ApprovalEventCrossCheck`），以及政策的狀態與轉移數上限（`PrecheckAsync` 只驗新版本身，客戶自己加過狀態時，合併後才超過）。T32 原本只涵蓋會 409 的守衛，這些 400 要到套用才出現。預覽以 T58 的候選（現況加上這一項與它的相依閉包）合併出的狀態機跑同一份驗證（抽成唯讀函式，設計器共用），不通過就標 `workflowInvalid`，`detail` 附違規的轉移或驗證訊息。
- **候選要帶上相依的新東西**（T58，主控已定，可推翻；複核 N2）：只用「現況加上這一項」會誤判兩種常見情況。新轉移指向這次新增的狀態（A25），候選裡沒有那個狀態（它是另一項），`stateIds.Contains(t.To)` 不成立，被判 `workflowInvalid`；新狀態的選項這時也還沒有 id，候選根本組不出來。需簽核的轉移以這次新增的流程為目標（A52、A56），`ApprovalConstraints.Validate` 的 `flows` 取自 `flows.ListCurrentByModuleAsync`，只有資料庫裡的流程，會報 `NoFlow`，`rejectTo` 與閉包檢查也跑不到新流程的定義。所以：
  - 候選等於現況，加上這一項，再加上它 `dependsOn` 的遞移閉包（N 裡的新選項、新狀態、新流程，以及 T43 第 2 點的改了 `to` 的既有流程）。
  - 還沒建立的物件給臨時負數 id（同一次預覽內唯一）。`Validate` 的標籤查不到時退回 `id.ToString()`，不會壞。
  - 交給 `ApprovalConstraints` 的流程清單是現況的流程，加上閉包裡 N 的新流程與改了 `to` 的既有流程（以修改後的定義取代現況那一份），經 codec 轉成 `FlowState`。
  - `PendingApprovalGuard`、`LockedDataGuard`、`PriorityTakenAsync`、`CheckRetargetAsync` 用同一套候選：新狀態上沒有記錄、新流程沒有實例，不影響判斷。
- **失敗**：同 §9.1，第一個失敗就停、整批回滾。修改的錯誤鍵前面加項目識別（pkg1c 的 `Fail`）；新物件沿用 `AppFlowInstaller` 的前綴（`<模組代號>.workflow.…`、`events.<代號>.…`、`approvalFlows.<代號>.…`）。
- **權限**：這些設計器指令都要設計器 Edit，主檔成員模組另要系統管理員（`MasterDesignerBehavior`）；事件勾了 `allowHiddenSource` 要權限設定（`HiddenSourceGate`）。升級本來就要系統管理員＋設計器 Edit＋權限設定（§12），不另加。
- **順序**（T31，主控已定，可推翻；審查 D1、D2）：§9.1 第 8 步細化成「狀態機第一趟 → 分錄 → 事件（沖銷別人的排在被沖銷的之後，`InDependencyOrder`）→ 檢查 → 簽核流程 → 狀態機第二趟 → 轉換 → 列印範本 → 報表 → 任務規則」，同 `AppFlowInstaller`；每個階段**先新增、再修改**，讓修改引用得到同階段的新物件（例如既有事件改成沖銷這次新增的事件）。
  - 狀態機第一趟**保留現況每條轉移的需簽核原樣**。只有「這次才加上需簽核、而套用當下資料庫裡目標狀態上沒有流程」的轉移，第一趟先不帶需簽核，等簽核流程那一階段建好或改好，第二趟補上；目標上已經有流程的，第一趟就直接帶（複核 R1：看的是套用當下的目標狀態，所以也涵蓋未用過的既有流程這次把 `to` 改到這個狀態的情況，那個修改排在簽核流程階段，第一趟時資料庫的流程還沒改過去）。沒有這種轉移的模組不跑第二趟。照抄開啟「第一趟一律不帶需簽核」不行：開啟時整份狀態機都是新的，升級的第一趟卻是以現況為底，拿掉既有轉移的需簽核，有簽核中的單時 `PendingApprovalGuard.RejectWorkflowChangeAsync` 回 409，有記錄停在鎖定狀態時 `LockedDataGuard.RejectUnlockAsync` 也回 409；Demo、進銷存這類有簽核資料的客戶，任何一項狀態機修改都會整批回滾。
  - **貢獻移到第 5 步**，和欄位一起建，讓轉換、報表、任務規則引用得到新貢獻欄位；整合仍在第 9 步，調和移到最後（第 11 步，T52）。

#### 9.6.2 逐類規則

每類寫：識別與粒度／新增／修改／相依／不能套用的情況／會影響既有記錄或進行中實例的處理。原因代碼見 §9.6.4。

**狀態機**（模組一份；比對項目分成狀態機本身 `workflow:<模組>`、狀態 `state:<模組>.<選項>`、轉移 `transition:<模組>:<起>><訖>`）

- 粒度：狀態機本身比狀態欄位與初始狀態；狀態比唯讀、簽核可編輯；轉移比群組與需簽核。套用時以資料庫現有的 `Workflow` 為底，把勾選的狀態、轉移換成 id 合進去（T44），一個模組每一趟只送一次 `SaveWorkflowRequest`（建立與更新同一個指令，以模組 key 為參數）；第一趟保留現況的需簽核，需要第二趟的情況見 §9.6.1 順序。
- 新增：新狀態依賴它的選項（選項是新版新增時一起勾）；新轉移依賴起訖狀態（pkg1b 已補）；需簽核的新轉移另依賴目標上的新流程（T43 第 2 點，現況目標上沒有流程時）；狀態機本身依賴新的初始狀態（T43 第 6 點）。新轉移的群組照群組對應換，並在預覽列成 `attachedPermissions`：推轉移是給權類，標「給權」，比照 Q12（T57，顧問分流 L3、Q15 附條件）。群組全部對到略過的整條不建、記 warning，同開啟的 fail closed（`AppFlowInstaller.TransitionSkipped`）。
- 修改：初始狀態照一般規則，只影響之後新增的記錄。
- 狀態欄位不同 → 無法套用（`statusFieldChanged`，比照欄位型別；換狀態欄位等於換掉整個流程，簽核守衛也會擋）。
- 新版移除的狀態與轉移只列出、不刪（Q4）；因為套用一律以現況為底，`PendingApprovalGuard` 要求「進行中實例用到的狀態、轉移仍在」自然成立。新版把狀態改名（移除舊選項＋新增新選項）時，記錄留在舊狀態（**Q13**）。
- 新版的其他項目把引用從被移除的狀態改到新狀態（例如連動事件原本在「已作廢」觸發，新版改在「已取消」觸發），照一般規則分類、預設勾；那一項的 `impacts` 帶 `stateReferenceMoved`（`detail` 附舊、新狀態），被移除的狀態那一項帶 `retiredStateReachable`，提示「建議到狀態機設計器拿掉進入它的轉移」（**Q26，待使用者確認**）。判斷方式（T61，主控已定，可推翻；複核 R2）：
  - 狀態引用會出現在：事件 `trigger.from`／`trigger.to`、`when` 裡狀態欄位的 `opt_<代號>`、轉換 `sourceStates`、簽核流程 `to`／`rejectTo`、任務規則的觸發值、共用檢視、規則、報表篩選。`RefsOf` 是一份平的集合，分不出哪個屬性引用了哪個狀態，所以不逐位置解析，改成：對項目的每個屬性，在那個模組的狀態選項代號裡，以字串比對屬性的 JSON（裸代號、`opt_<代號>`、`<模組>.<代號>` 都算）。
  - `stateReferenceMoved`：某屬性在 B 的 JSON 含有一個在 N 被移除的狀態代號，在 N 的 JSON 不再含它、改含同模組這次新增的狀態代號。
  - `retiredStateReachable`：狀態是 `removedInNew`，而且 C 有進入它的轉移。
  - 兩者都只是資訊型提示，字串比對誤判（例如欄位代號剛好和狀態代號相同）可以接受。
- 狀態從唯讀改成可改、而有記錄停在那裡 → 無法套用（`unlocksRecords`，附 `affectedRecords`）；從可改改成唯讀可以套，預覽註明筆數（`impacts: recordsInState`，**Q14**）。一般唯讀的解鎖是升級專用規則、設計器不擋；簽核鎖定狀態被解鎖由共用的 `LockedDataGuard` 判斷，同一個原因代碼（T46 第 2 點）。
- 既有轉移的群組修改 → 只列出、不能勾（`transitionGroups`，**Q15**）。條件（複核 N4）：轉移的 `groups` 屬性 N 與 C 不同，而且分類不是「只有客戶改」。這樣才涵蓋沒有基準（`noBaseline`）與基準沒有、客戶卻已有同一條轉移（分類成兩邊都改）的情況；既有權限的擋法本來就不看分類（`AppUpgradePreviewer.cs:301`），這裡照同一個原則，不只擋「只有新版改、兩邊都改、上次略過」。
- 既有轉移**加上**需簽核 → 可以套，目標狀態要有流程（`ApprovalConstraints`）；現況目標上沒有流程時，N 裡目標為它的流程列進 `dependsOn`（T43 第 2 點）。加上之後，目標狀態和沿一般轉移走得到的下游狀態立刻變成簽核鎖定（簽核設計 §9.3：看狀態，不看實例），已停在那裡的記錄跟著被鎖，所以照 Q14「改成唯讀可以套」處理：可以勾，`impacts: recordsInState` 註明會被鎖的筆數。另外，客戶自己加過、進入同一個鎖定狀態的一般轉移，會讓合併後的狀態機過不了「進入鎖定狀態一律要簽」，預覽的整份驗證標 `workflowInvalid`、附那條轉移（T47）（**Q16**）。
- 既有轉移**取消**需簽核：有簽核中的單 → 無法套用（`approvalInFlight`，附簽核中張數）；沒有簽核中、但目標狀態或它的下游有記錄（取消後會被解鎖）→ `unlocksRecords`（附筆數）；鎖定狀態上沒有記錄時可以勾（**Q16**）。

**簽核流程**（`approvalFlow:<Key>`，Key 全站唯一）

- 新增：`CreateApprovalFlowRequest`，依（模組、目標、優先序）排序建立（同開啟）；略過的群組照 `AppApprovalFlowCodec.Substitutions` 由流程備援或政策預設頂替，warnings 列出（§22.1 最後一點在這裡做完：B、N 比對前也先套同一份頂替，§6.2.1 第 4 點，T42）。新增的流程不受下面「簽核人」那條限制：沒有既有授權可衝突，同 Q5 的新模組。
- 修改：`UpdateApprovalFlowRequest`（只帶 Key），合併在群組 id 層做（T44）。目前版本被用過且定義有變時，指令自己產生新版本；進行中的單照原版本走完（§9.4，簽核設計 §4.4）。預覽在項目上加 `impacts: inFlightApprovals`（附張數）。
- **簽核人**（**Q27，待使用者確認**）：比對把簽核人從關卡裡拆出來，成為獨立的 `approvers` 屬性（拆法見下一點 T59）。下列任一成立，整項無法套用（`approverGroups`），原因「簽核人是你的內控決定，請到簽核流程設計器調整」：
  - `approvers` 屬性 N 與 C 不同，而且分類不是「只有客戶改」（複核 N4）。只看「只有新版改、兩邊都改、上次略過」會漏掉沒有基準（`noBaseline`，`UpgradeClassifier.cs:62-67` 可以勾）與基準沒有、客戶已有同 Key 流程（`:68-73`，分類成兩邊都改）的情況，勾了就用新版覆寫客戶的簽核人，屬於權限問題。轉移的 `transitionGroups` 用同一句定義（§9.6.2 狀態機）。
  - 要寫入的 `stages`（分類是只有新版改、兩邊都改或上次略過，勾了就取 N）的關卡代號集合和 C 的不同（複核 N3）。例子：客戶在流程裡自己加了第三關（`stages`、`approvers` 都只有客戶改），新版只改第一關的名稱；`stages` 變成兩邊都改、可以勾，勾了取 N 的兩關，C 的第三關簽核人配不到關卡，客戶自己加的那一關就不見了，等於透過升級削弱客戶的內控。客戶刪掉一關、新版又改那一關也一樣配不出簽核人。
  - 只改關卡名稱、條件等其他內容，而且關卡代號集合相同 → 照一般規則可勾。`approvers` 只有客戶改時保留客戶的：套用時依關卡代號逐關把 N 的其他內容配上 C 的簽核人。
- **簽核流程的屬性拆法**（T59，主控已定，可推翻；複核 N3）：`AppApprovalFlow` 留在 `UpgradeItems.AutoCompared`（`UpgradeItems.cs:111`），比照報表 `shareWith` 的做法（`:176-177`）：
  - `Generic(f with { FallbackApprovers = null, Stages = 每關 s with { Approvers = 空值 } })` 產生流程的其他屬性，其中 `stages` 是每關去掉簽核人後的內容；關卡的其他屬性（含 `code`）跟著序列化自動比，之後 fg6 或任何一段替關卡加屬性也不會被漏掉。
  - `approvers` 另外算，形狀是 `{ <關卡代號>: 該關的 approvers, "$fallback": fallbackApprovers }`，以關卡代號為鍵；`Normalize` 會排序鍵，原廠調整關卡順序不會被誤判成改了簽核人。群組先經 §6.2.1 正規化與 T42 的備援頂替。
  - 不移進 `HandCompared`：手工清單裡的 record，覆蓋率測試只沿「不比對」的屬性往下走（`UpgradeClassifierTests.cs:125-140`），`AppApprovalStage`、`AppApproverSource` 會從此不受覆蓋率保護；手列關卡內容（名稱、條件、模式…）也會在之後加屬性時被基準換新默默吞掉，正是 §13 要擋的事。覆蓋率測試不必改，U1 照跑。
- 被用過的流程新版改了目標狀態 → 無法套用（`flowInUse`，設計器指令會擋）。
- 優先序（T50，主控已定，可推翻；審查 S4）：新流程的（模組、目標、優先序）已被客戶自建的流程佔用 → 無法套用（`priorityTaken`），提示到設計器調整優先序再重新預覽（**Q17**）。既有流程的優先序修改同樣以「現況加上這一項」判斷，撞到現況其他流程就 `priorityTaken`。同一份新版裡兩個流程互換優先序（例如進銷存的 `inv-po-large` 與 `inv-po-medium`），逐筆 Update 一定先撞唯一性檢查，兩項各自判斷都會撞，都標 `priorityTaken`。不用暫時的優先序自動互換：那要多一套只為升級存在的寫入路徑，互換期間的中間狀態也要再過一次驗證；管理員到設計器互換一次就好。
- 新版移除的流程只列出；客戶要淘汰就自己停用（被用過的流程不能刪，只能停用）。
- 相依：流程依賴目標狀態與退回狀態（`state:<模組>.<to>`、`state:<模組>.<rejectTo>`，T43 第 3 點）、條件與可編輯欄位引用的欄位；需簽核轉移依賴目標上的流程（T43 第 2 點）。

**單據轉換**（`conversion:<Key>`）

- 新增 `CreateConversionRequest`；修改 `UpdateConversionRequest`（Key、來源與目標模組不能改；新版改了來源或目標 → 無法套用 `kindChanged`）。兩者都經 `ConversionInputOf`（T29）。
- 轉換只影響之後的轉換：已轉出的單據沒有關聯表，已轉量由 `ConversionLedger` 即時算：從目標表頭的追溯欄位找起（`TargetsOfAsync` 用 `Header.SourceFieldId`），再找目標明細，加總 `Quantity.To`；`Quantity.From` 決定剩餘量。所以名稱、啟用、可轉狀態、帶值欄位（`header.copy`、`lines.copy`）、固定值（`header.set`）照一般規則套。
- **追溯或數量欄位改了、而且已經有轉出的單據** → 無法套用（`conversionInUse`，附筆數）（**Q18**）。觸發條件（T48，主控已定，可推翻；審查 D7）：N 與 C 的 `header.sourceField`、`lines.sourceModule`、`lines.targetModule`、`lines.sourceLineField`、`lines.quantity.from`、`lines.quantity.to` 任一個不同（含 `lines` 整個新增或拿掉），而且目標模組已有記錄的表頭追溯欄位（現況的 `header.sourceField`）有值。只改表頭追溯欄位也算：舊的已轉單據會全部找不到，剩餘量回到全額，可能重複出貨。比對引擎把 `header`、`lines` 各當一個屬性，所以這裡要往下比子欄位，不能只看屬性的分類：同一個 `header` 屬性的差異，只改 `copy` 可以套，改到 `sourceField` 就不能。計數只數表頭，判斷有沒有轉出過已經夠用（手動填了參照的單也算進去，偏保守）。原因文字寫明「到設計器手動改一樣會重算剩餘量」：第一張單轉出後這一項就永遠不能勾，管理員要知道換到設計器改也有同樣的影響（顧問分流 Q18 附註）。
- 相依：來源與目標的欄位、可轉狀態的選項。

**連動事件**（`event:<Key>`）

- 新增 `CreateEventRequest`（沖銷別的事件的排在後面）；修改 `UpdateEventRequest`（Key、來源模組不能改）。
- 只影響之後的寫入，不回頭補做（事件設計 §10.5）：新版加的效果，已記帳的來源不會補記。
- **新版拿掉了這個事件已觸發過的效果代號**（`Dynamic_EventFact` 有這個事件、這個效果代號的事實）→ 無法套用（`firedEffect`）：效果代號是冪等鍵，換代號等於新效果，同一張單再觸發時會再記一次帳（**Q19**）。只有 create、reverse 效果會留事實，update 效果不受影響。只加效果、改既有效果的欄位對應或條件可以套。
- `firedEffect` 的判斷與範圍（T49，主控已定，可推翻；審查 S5）：`IEventRepository` 現有的事實查詢都要帶 `sourceRecordId`，新增一個「依（事件 Key、效果代號）查有沒有事實」的查詢，查到一筆即可。同一個效果代號換了 `kind`、`target`（目標模組）或 `each`（逐明細；冪等鍵的 `ItemKey` 從 0 變成明細 id，pkg1d1b 審查 M1），而那個代號已有事實，也標 `firedEffect`：舊事實指向的是當時效果寫到的目標記錄，換了種類、目標或逐明細，之後沖銷、再觸發時對不上或重複記帳。
- 相依：事件依賴來源與目標模組、欄位、觸發狀態；沖銷效果依賴 `ofEvent` 的事件與它目標的分錄設定。

**跨記錄檢查**（`check:<Key>`）

- 新增 `CreateCheckRequest`、修改 `UpdateCheckRequest`（Key、模組不能改）。兩者都會讓 `CheckIndexer` 自動開「可篩選」並回填索引，notice 併進 warnings；預覽只呼叫拆出來的純判斷，不寫資料（T46 第 3 點），可篩選的變化列成 `impacts: autoFilterable`。
- 只檢查之後的寫入，不重掃既有記錄；檢查改嚴後，不符的舊記錄要等下次寫入同一組時才被擋（**Q20**）。
- 需要回填索引、而模組記錄數超過政策 `check.maxBackfillRecords` → 無法套用（`backfillLimit`，設計器指令會擋，回 409；上限是既有政策，不另設）。
- 相依：分組、加總、上限、`where` 引用的欄位。

**分錄**（`ledger:<模組>`，這裡的分錄是「不可修改分錄」設定，事件設計 §6，不是會計傳票）

- 新增或修改都是 `SaveLedgerRequest`（建立與更新同一個，以模組 key 為參數）。
- 新模組的分錄設定隨模組一起裝、不另列，引用它的項目依賴的是 `module:<代號>`；既有模組這次新設分錄，才另列 `ledger:<模組>`（A35）。
- 既有分錄設定的沖銷欄位、取負、互換改了，而模組已有記錄 → 無法套用（`ledgerLocked`，指令本來就擋「分錄已有記錄，沖銷設定不能再修改」；理由是舊分錄的沖銷要用當時的設定才能精確抵銷）。
- 新版把**已有記錄**的既有模組設成分錄 → 無法套用（`ledgerFreeze`，附筆數）：升級不替管理員按 `confirmFreeze`，要到設計器自己確認（**Q21**）。沒有記錄時照一般規則套。
- 相依：沖銷欄位、取負與互換的欄位；有狀態機的模組不能設成分錄（`LedgerValidator.cs:21`，指令驗證）。

**列印範本**（`printTemplate:<Key>`，Key 在模組內唯一）

- 新增 `CreatePrintTemplateRequest`、修改 `UpdatePrintTemplateRequest`（模組＋Key）；本文經 `AppPrintCodec` 把欄位代號換成 id。範本沒有版本歷史，套用就是覆寫本文。
- 本文是一個屬性：客戶改過、新版也改 → 兩邊都改、預設不勾，三份本文用「檢視」對話框看（§10.3）；勾了就以新版本文取代，啟用狀態、名稱裡客戶改的語系保留（**Q22**）。舊本文可從稽核的逐項舊新值找回（pkg1-8）。
- 本文引用的欄位被客戶刪了：相依驗證會要求勾回那個欄位（客戶已刪除項目），不勾回 400；不走開啟時「印空白並警告」的路。
- 相依：本文的 `{{欄位}}`、`{{#each 明細模組}}` 的模組與迴圈裡的明細欄位（T43 第 4 點）；範本所在的新模組（T43 第 1 點）。

**任務規則**（`taskRule:<Key>`，Key 全站唯一）

- 新增 `CreateTaskRuleRequest`，帶 `AppId` 為本應用程式（關閉時停止觸發，同開啟）；修改 `UpdateTaskRuleRequest`（模組＋Key，`AppId` 不動）。
- 規則只影響之後的觸發；已產生的任務不改。未完成、沒手動改過的任務，下次來源記錄寫入時照任務設計 §5.5 用規則**現在**的定義同步，所以新版改了偏移天數或負責人欄位，會在之後的同步生效；手動改過的不動。`once` 的觸發紀錄（`TaskRuleRun`）跟著 Key，已觸發過的記錄不會因為更新再觸發。新版從規則拿掉的任務項目，已產生的那批任務保留（**Q23**）。
- 規則所在模組沒啟用任務：同開啟，自動啟用並警告，預覽先列 `impacts: enablesTasks`。
- 自動暫停的規則更新後仍暫停（指令本來就不解除），預覽不另處理。
- **掛在主檔模組上的任務規則**（T54，主控已定，可推翻；審查 D11）：任務規則的 `Module` 可以是主檔符號（`AppTaskRule` 允許），`IsSecondBatch` 以 `Module` 含 `/` 判斷，會把它們一直擋到 pkg1d2，而 pkg1d2 刪掉 `SecondBatch` 後又會沒人設計、沒人驗就放行。所以歸 pkg1d1b：`/` 規則只套在欄位、區塊、選項、貢獻、權限類項目與報表，不套在 Coded 類 section（轉換、事件、檢查、列印範本、任務規則、簽核流程）。pkg1d1a 期間 `/` 規則原樣（Coded 類 section 本來就大多還在 `SecondBatch`）。新增走 `InstallTaskRulesAsync`（本來就支援主檔符號），修改走 `UpdateTaskRuleRequest`（主檔成員模組要系統管理員，升級本來就要）；驗收 A62。轉換、事件、檢查的 `Module` 是來源模組，目標寫主檔符號時本來就不受 `/` 規則影響，一併寫進 A62 的反向格。
- **`mainModule` 是主檔符號的報表**（T60，主控已定，可推翻；複核 R4）：報表的 `Module` 取 `mainModule`，同樣可能含 `/`，但 pkg1c 的 `SaveReportsAsync` 沒驗過主檔符號的報表。pkg1d1b 改 `/` 規則時報表**維持擋下**（照列、`notYetSupported`、`secondBatch`），和主檔符號換算（T43 第 5 點）一起在 pkg1d2 開放；pkg1d2 刪掉 `SecondBatch` 前補驗收 A74，確認新增與修改都照主檔符號換成主檔模組的 id。
- 相依：觸發欄位與值（選項）、負責人與到期日欄位、條件引用的欄位；引用主檔欄位時照 T43 第 5 點換算（pkg1d2；在那之前，用到的主檔有新版時整個套用被 `masterPending` 擋下）。

**貢獻**（`contribution:<主檔>/<模組>` 加它底下的欄位、選項、權限項目；對照列的名稱含 `/`）

- 新增貢獻、既有貢獻區塊裡的新欄位：照 pkg1c 新欄位的做法，交 `TemplateInstantiator` 的 `ContributionInput`，`Prefix` 是主檔符號、`ReattachBlockId` 是貢獻區塊（新貢獻就新建區塊），寫 `AppField`／`AppBlock`／`AppOption` 對照列。貢獻欄位本來就不得必填（套件驗證）。
- 修改：一般的 `UpdateField`／`UpdateBlock`／`UpdateOption`（目標是主檔成員模組，`MasterDesignerBehavior` 要系統管理員）。
- 權限照 Q12 與 §9.1 第 7 步：寫本應用程式名下的來源記錄、補 `FieldGrant`、最後 `MasterLifecycle.RecomputeAsync`；既有貢獻的權限修改只列出。
- 貢獻只能引用主檔的基本欄位；引用的是主檔新版才有的欄位時，依賴主檔段的那一項（§9.6.3，T43 第 5 點）。
- 新版移除的貢獻欄位只列出（Q4）；主檔資料上的值保留。

**整合**（`integration:<code>`，比整份宣告的頂層屬性）

- 現況 C 的整合取保存的宣告（`App.IntegrationsJson`），客戶在設計器改了整合安裝出來的欄位、事件、檢查，比對看不出來。所以預覽另看 `AppIntegration`：整合是 `Blocked`（`itemConflict`、`itemMissing`、`unbound` 等），或安裝出來的項目和保存的宣告不一致 → 無法套用（`integrationConflict`），提示照整合設計 §5.4 先還原、retry（**Q24**）。「一致」的判斷從 `IntegrationReconciler` 抽出唯讀的一致性比對（`EnsureAsync` 比對的那一段，不建不改），調和與預覽共用。
- **夥伴缺新版才有的模組**（T51，主控已定，可推翻；審查 D8）：整合的夥伴（`with`）不在 `requires` 裡（`RequiresOf` 只收 apps、entities、masters），§8.2 的 `requiresUpdate` 擋不到；不擋的話，套用後調和判成 `unbound`、整合被擋下，只留一行警告。所以預覽用新宣告跑 `IntegrationWorld.LoadAsync`：夥伴應用程式已開啟、但新宣告引用的夥伴模組或欄位解析不到 → 無法套用（`integrationUnbound`，`detail` 是夥伴應用程式 id），提示先更新夥伴。夥伴沒開時不判斷，照下面「沒安裝過」只換宣告。
- 可以套時（T40，主控已定，可推翻；審查 D8、S12），分支看整合**有沒有安裝過**（`AppIntegration.Installed`），不只看狀態：
  - **已安裝**（不論 `Active`、`Disabled`、`Suspended`、`Held`）：先把已安裝的項目改成新宣告。既有事件、檢查走 `UpdateEventRequest`／`UpdateCheckRequest`；既有整合欄位的標籤等屬性走 `UpdateField`（`EnsureAsync` 只比型別與參照對象，其他屬性改了不會判衝突）；新欄位走 `AddFieldRequest`，新事件、新檢查走 `Create*`，**新建的每一項登記進 `ItemsJson`**：沒登記的話，調和看到登記裡沒有、資料庫裡卻已有的事件或檢查會判 `codeConflict`，沒登記的欄位會先找不到、再因 `allowCreate: false` 判 `itemMissing`。新版從宣告拿掉的項目只列出、不刪（Q4），從 `ItemsJson` 移除登記，之後不再受調和管。`SuspendedActive` 等暫停語意照舊，升級不改整合的開關。然後換 `IntegrationsJson` 那一筆、補 `AppIntegration` 列。只換宣告、不改安裝項目的話，之後一恢復，調和會把定義不同的判 `itemConflict`、新欄位判 `itemMissing`，整合被擋下、項目全部停用；以 MES 的 `stockOut` 來說，出貨就不再扣庫存。
  - **沒安裝過**（例如夥伴一直沒開）：只換宣告，之後安裝時照新宣告。
  - 調和不在這一步：§9.1 第 11 步在同一個交易、最後一次 `CommitAsync` 之後才跑（T52）。
- 相依：擁有者自己的模組與欄位；夥伴的符號（`<應用程式 id>/…`）不在本應用程式的比對項目裡，由上面的 `integrationUnbound` 判斷。

#### 9.6.3 共用主檔一起更新（Q10、Q25）

- **預覽**：pkg1b 已回 `masters`（每份主檔自己的 `groups`、`items`、`counts`）。主檔套件只收群組、模組、欄位例外、報表（不帶流程），所以主檔的項目全部屬於第一批的種類，套用沿用 pkg1c 的程式，以主檔自己的基準、群組對應、現況跑一次（T36，主控已定，可推翻）。主檔模組的權限：新模組寫 `GrantSource.Master` 來源記錄，既有的只列出（§6.2）。
- **候選新版不帶客戶自己加的欄位**（T53，主控已定，可推翻；審查 D10）：主檔已開啟時再匯入，存下的合併副本是資料庫匯出（`fromDb`），客戶在設計器自己加的主檔欄位沒有對照列，匯出時代號是 `f_<id>`。`MasterCandidateAsync` 把「內建新版合併舊副本」當成新版 N，這些欄位就跟著進了 N；C 用對照列過濾、不收它們，B 是開啟當時的原文、也沒有，於是被分類成 `added`、預設勾，pkg1d2 開放主檔套用後會照 N 再建一份重複欄位（pkg1b、pkg1c 只在預覽多一列假的「新增」，還沒寫進資料庫）。所以算候選新版時，副本裡不在主檔對照列的比對代號（`f_`／`b_`／`o_` 開頭的，或主檔 bindings 裡沒有的）不進 N。這條是讀程式推出來的、未實測，**實作者先寫失敗測試確認**（A68），確認後再改 `AppUpgradePreviewer.MasterCandidateAsync`。
- **body**：預覽與套用的 body 加 `masterGroupMap: { 主檔 id: { 代號: choice } }`，形狀同 `groupMap`，規則同 T26（只能改新代號、失效的、略過過而新物件用得到的）；目前程式比主檔時固定帶空對應（`new UpgradeBody(null, null)`），只能用建議。套用 body 的 `masters: { 主檔 id: [項目識別] }`（`UpgradeApplyBody.Masters` 欄位已在，pkg1c 沒讀）照 §8.3 的勾選驗證（T35，主控已定，可推翻）：主檔 id 不在這次預覽的 `masters` → 400，鍵 `masters.<主檔 id>`；項目不在清單、不能套用、缺相依 → 400，鍵 `masters.<主檔 id>.items.<項目識別>`（A69）。
- **token**：pkg1b 起已涵蓋每份列出的主檔（`tokenParts`），pkg1d 再把 `masterGroupMap` 加進雜湊。A3b（甲在進銷存頁套了往來對象，乙用 CRM 頁的舊 token）因此回 409 `upgradeStale`，乙重新預覽後主檔段不再出現。
- **跨份相依**（T37，主控已定，可推翻）：應用程式的項目引用主檔新版才有的欄位、選項（例如新報表用到往來對象新增的「傳真」），`dependsOn` 寫 `master:<主檔 id>/<項目識別>`，前端照樣連勾，後端照樣驗。應用程式這邊引用主檔欄位寫主檔符號，`References` 照 T43 第 5 點換算後再對。
- **被依賴、但上次略過的主檔項目**（T56，主控已定，可推翻；顧問分流 L2、Q25 附條件）：主檔前進到 1.1.0 時略過了「傳真」，之後進銷存新版的報表用到傳真，主檔卻沒有新版，`masters` 段不出現，相依永遠滿足不了；到設計器手補只得 `f_<id>`，代號對不上。所以應用程式的項目依賴的主檔項目若在主檔基準的 `SkippedJson` 裡、客戶值也沒改（仍算「上次略過」），即使主檔沒有新版，也把**那幾項**列進 `masters`（`fromVersion` 等於 `toVersion`），標「上次略過」、預設不勾，連勾照一般相依。套用時只寫勾的那幾項，主檔的版號與基準原文不變，`SkippedJson` 拿掉這次勾回的（A71）。`requires.apps` 跨應用程式也有同樣的卡死，pkg1d 不做，見 §22.2。
- **主檔之間**：主檔也可以依賴主檔（聯絡人依賴往來對象）。兩份都有新版時，依 `requires.masters` 排序，被依賴的先套（§9.1 第 1–2 步）。
- **主檔一律隨這次套用前進**（**Q25**）：列在 `masters`、有新版的主檔，套用時版號、基準一起換成新版，沒勾的項目記進主檔基準的 `SkippedJson`，下次標「上次略過」（同 §9.2）。不提供「這次只更新應用程式、主檔先不動」。
- **基準與合併副本**（T38，主控已定，可推翻）：主檔基準整列換新（`GroupMapJson` 補這次的主檔群組對應）。以內建新版升級、而客戶有再匯入的合併副本時，`Dynamic_AppPackage` 那份副本改寫成「內建新版合併舊副本」（§7.1；pkg1b、pkg1c 只在預覽算這份，還沒寫回；舊副本裡沒有對照列的代號照 T53 不併入），基準存同一份序列化文字，兩邊相同才不會下次比出假差異（同 §5.2 v1 範本檔的例外理由）。這裡存的是定義層的合併，不是再匯入時 `MergeAsync` 那種資料庫匯出（`fromDb`）（審查 S16）：資料庫匯出帶著客戶在設計器的修改，存成基準會讓客戶的修改變成「原廠給的」（B＝C），下次新版改到同一處時被分類成「只有新版改」、預設勾，蓋掉客戶的修改；副本用來在刪除後重新自動開啟，客戶的設計器修改那時本來就不在了，定義層合併就夠。
- **只有主檔有新版**（T55，主控已定，可推翻；審查 S10、S13、S14）：應用程式自己的 `items` 為空，套用只動主檔；應用程式的版號、基準、略過紀錄不變。現在的程式做不到：`BuildAsync` 對主檔 key 回 `MasterManaged`，而 `ApplyAsync` 在 `mine.Context` 為 null（應用程式自己沒有新版）時直接擋下（`AppUpgrader.cs:65`）。所以 `ApplyAsync` 拆成以比對結果（Comparison）為參數的核心，應用程式與每份主檔各呼叫一次，應用程式沒有新版就跳過應用程式那一次。預覽的 `canApply` 只看主檔段與共同的 blockers；套用回 200 與 `AppResponse`（A70）。
- **`masterPending` 拿掉的條件**：pkg1d 處理主檔的那一段（§9.6.7 的 pkg1d2）合併時刪掉 `masterPending` 與它的翻譯鍵；同時 `SecondBatch` 集合清空，`secondBatch` blocker 與 `notYetSupported` 原因代碼一起刪（T39，主控已定，可推翻）。
- **稽核**：主檔一份一筆 `app.upgrade`（目標是主檔，手動 `auditLog.Add`），和應用程式那筆同一個 `RequestId`。只有主檔有新版時，外層那筆 `app.upgrade`（目標是應用程式）照寫：摘要的 from 等於 to、套用項目數只算主檔的，逐項明細為空、指向主檔那幾筆（T55）。

#### 9.6.6 ERP 對照（第二批）

以下依主控對主流產品的了解整理，未另行上網查證；檢核清單照 ERP 資料模型 §7。

- **進行中的流程綁版本**：SAP 的彈性工作流程，進行中的實例綁啟動時的流程版本（簽核設計 §2 已引）；本設計照用（§9.4），升級改流程只影響之後送出的單。
- **已過帳不可回溯**：SAP、Odoo 過帳後的憑證都不能改，要用沖銷或折讓；設定變更只影響之後的單據。對應到這裡：不可修改分錄已有記錄時不改沖銷設定（`ledgerLocked`），有記錄的模組不由升級代為設成分錄（`ledgerFreeze`）；事件不回頭補記帳、不換已觸發的效果代號（`firedEffect`），單據過帳後的值本來就由事實鎖與「已固定的記錄不重算」保住（事件設計 §4.7、§10.4）。
- **出廠設定與客戶修改**：Odoo 升級模組時重新載入出廠資料，客戶改過的範本、自動化會被蓋回，除非標了不更新；本設計的列印範本、事件、規則照三方比對，客戶改過的預設不覆蓋。
- **已轉量即時算**：Odoo 的已出貨、已開票量由下游單據推算；本設計的轉換同樣即時算，所以改了數量對應會影響已部分轉出的單，列為不能套（`conversionInUse`），對照 ERP 資料模型 §3.4 原則 1「履約量由事實推算」。
- **檢核清單**：
  1. 重複概念：不新增模組、主檔或單據，不適用。
  2. 主檔欄位歸屬：貢獻只能引用基本欄位；主檔的基本欄位只在主檔段比與套（§9.6.3），一般應用程式的升級只碰自己的貢獻。
  3–4. 單據擁有者、上下游：不新增單據；狀態機、轉換、事件的修改走擁有者自己的設計器指令，整合仍只加在擁有者的模組，夥伴不被修改（整合設計原則）。需簽核的轉移仍用核心簽核流程。
  5. 數量與計數：轉換的數量對應在有已轉出單據時不改（Q18），不讓已轉量失真；取消類狀態、共用計數的語意不變。
  6. 開關組合：夥伴沒開時整合只換宣告，之後開啟照新宣告安裝；主檔被多個應用程式共用時，誰先套都可以，套完其他頁不再列（Q10、A3b）。只開一個應用程式時照常可用。
  7. 會計影響：升級不產生傳票、不重算已過帳的記錄；分錄（不可修改分錄）設定見上。
  8. 對照一般 ERP：見上四點。
  9. 核心能力：全部沿用既有設計器指令與守衛，沒有替應用程式開後門；新增的是「守衛的唯讀判斷」（設計器與預覽共用），以及兩條比設計器嚴、只在升級用的規則：一般唯讀狀態的解鎖（Q14）、既有簽核流程的簽核人只列出（Q27）。
- **簽核人屬於內部控制**：SAP、Odoo 的核准層級與核准人由客戶依組織設定，原廠範本只給起點；本設計對既有流程的簽核人只列出、不代改（Q27），和既有權限只列出（Q5）、既有轉移的群組只列出（Q15）同一個原則。

## 11. Demo 種子

### 11.1 做法（T15）

Demo 產生器開啟「CRM 與銷售」時，不開目錄裡那份，改開一份由程式從目錄版**推導出來的舊版**：

- 版號比目錄版小（實作者定，例如 1.3.0 → 1.2.9）。
- 少一個欄位、少一份報表（新版新增）；改一個欄位的泰文標籤（只有新版改）；改一個欄位的繁中標籤（配合下面客戶的修改形成兩邊都改）。
- 推導在程式裡做，不另存一份舊套件檔：舊檔會隨目錄版演進而過期。
- **推導在 JSON 文字層做**（審查必修 2）：拿目錄版的原文，用 `JsonNode` 依代號刪改後再序列化，產出的文字就是這次開啟的「原文」。
- **`AppOpener` 加一個內部入口**，接受「套件文字＋來源（`builtIn`）」，走同一條 `AppPackageSource.ReadAsync` → `AppOpenPlanner` 規劃 → 開啟的路徑；只給 Demo 產生器用，HTTP 不開。現有的 `OpenAsync(packageId, …)` 只能依 id 從目錄或匯入表取套件，照用的話基準會是目錄原文，B＝N，所有示範都失真（新版新增會變成客戶已刪除）。
- **基準存這份推導文字**（§5.2），`App.PackageVersion` 是推導版號。
- 推導拿掉的欄位不能被公式、彙總、規則、報表、轉換、事件、列印範本引用，否則推導版過不了套件驗證；拿掉的報表不能被儀表板引用。
- **實作與上面的差異（pkg1b 回填）**：推導版拿掉的是一個**選項**（行銷活動類型的「線上」），不是一個欄位加一份報表，新版新增只示範到選項。理由：CRM 的兩份報表都被 Demo 儀表板引用，拿掉就過不了推導條件；CRM 裡沒有一個欄位同時「沒被其他定義引用」又「沒被 Demo 情境填值」（情境填值的欄位在舊版不存在，情境就寫不進去），要拿欄位得改情境與其斷言，pkg1b 不做。代價是 Demo 示範不到新欄位的附帶權限標籤（Q12），附帶權限由 API 測試驗；pkg1c 做套用示範時若情境調整，再改成拿掉一個欄位。泰文、繁中標籤照上面做。

開啟後，產生器以「客戶」身分做幾個修改：

- 把同一個欄位的繁中標籤改成第三個值（兩邊都改，預設不勾，顯示原值）。
- 停用一個欄位（只有客戶改；若新版也改了它的標籤，套用後仍停用）。
- 刪掉一個沒有資料的欄位（客戶已刪除，預設不勾）。
- 在一個模組加一個自己的欄位（客戶新增，只算數量）。

被選的欄位與報表要避開 Demo 其他情境會用到、測試會斷言的（AGENTS.md「Demo 資料」：改種子前 grep 既有斷言，`.claude/rules/backend.md`）。進銷存、生產管理、共用主檔照目錄版開啟，用來示範「已是最新」。

**放在 pkg1b**（審查必修 3）：推導舊版與客戶修改隨 pkg1b 上線，pkg1b 合併時 Demo 就能示範預覽的各分類與入口權限；pkg1c 只補套用的示範。

## 13. 與 i3c（套件格式 9）的先後與相容

- **pkg1 不升 `formatVersion`**（T10）。比對在讀成 `AppPackageData` 之後做，基準與新版各自用自己的格式讀，所以兩邊格式不同照樣能比。
- **pkg1 先合併、i3c 後合併**：i3c 把內建三套件升到格式 9 時，`manifest.version` 一起升（i3 §8），已開啟的 Demo 與客戶會看到「有新版」：報表名稱多了三語是「只有新版改」，預設勾。i3c 要在比對引擎補兩件事，列進 i3c 的範圍：報表名稱從字串改成 `I18nText` 屬性（逐語系比）；`excludeFromAi` 只加不減（§9.4）。
- **i3c 先合併、pkg1 後合併**：pkg1 直接照格式 9 的物件寫比對，`excludeFromAi` 規則一開始就在。
- 兩種順序都不用改基準：基準是原文，舊格式永遠讀得懂。
- **共用檔**：兩段都動 `AppPackageData.cs`、`AppExporter.cs`，但 pkg1 不改格式、不碰 `backend/apps/*.app.json`（Demo 的舊版在程式裡推導），所以和 i3c、mg1「動套件檔不並行」的限制不衝突；仍不建議兩段同時在 `AppExporter.cs` 動工，誰後合併誰 rebase。
- 之後每次內建套件升版（fg6、s2e 等），pkg1 就是送到客戶手上的路徑。新格式帶來的新屬性，該段要在比對引擎補對應的項目或屬性。沒補的屬性不會產生差異，U1 照樣通過，抓不到；新版真的改了它時預覽不列，套用後基準整份換新（§9.2），這個修正就永遠送不到客戶。擋這件事的是 §18 的**覆蓋率測試**：`AppPackageData` 以下每個屬性（含 `FieldConfig` 的鍵）都要歸進比對對照表或明文的「不比對」清單，新屬性沒歸類測試就失敗，逼新格式的那一段當場補比對。

## 14. ERP 對照

以下依主控對主流產品的了解整理，未另行上網查證。

- **開源 ERP（Odoo）**：模組升級時重新載入模組附帶的資料檔，客戶在資料庫裡改過的出廠記錄會被覆蓋，除非那筆標了「不更新」；客製多半寫成另一個繼承模組，不直接改出廠物件。Formwright 讓客戶直接改出廠物件，所以需要三方比對，不能整份重載。
- **傳統大型 ERP（SAP）**：系統升級時有「修改調整」工具，列出客戶改過、原廠也改了的開發物件，逐項選擇採用原廠版本或保留客戶修改，和本設計的「兩邊都改」最接近。差別是它在升級當下強制處理；Formwright 讓管理員什麼時候想更新再更新。
- **雲端平台的受管理套件（Dynamics 365 的分層方案）**：原廠套件是底層，客戶修改是上面一層，畫面取最上層；升級只換底層，客戶那層保留。本設計的「客戶改過的預設不覆蓋」是同一個精神，但 Formwright 只有一層實際資料，所以用基準記住「原廠當初給的」。
- **檢核清單（ERP 資料模型 §7）**：
  1. 重複概念：不新增模組、主檔或單據，不適用。
  2. 主檔欄位歸屬：升級一般應用程式只碰它自己的貢獻欄位；主檔的基本欄位只在升級主檔時比，歸屬規則照共用主檔設計 §9（§6.2）。
  3–5. 單據擁有者、上下游、數量：不新增單據，不適用；轉換與事件的更新沿用既有指令與驗證。
  6. 開關組合：升級 A 不刪任何東西，B 對 A 的引用不會斷；A 的新版需要 B 的新模組時要先更新 B（§8.2）。只開 A 時照常可用。
  7. 會計影響：不產生傳票；「分錄」在這裡是不可修改分錄的設定（事件設計 §6），已有記錄時不改沖銷設定、不代為設成分錄，事件不回頭補記帳（§9.6.2、§9.6.6）。
  8. 對照一般 ERP：見上三點。
  9. 核心能力：比對與套用都用既有的設計器指令，沒有替應用程式開後門。

9. **2026-11-19 平台分流的主控技術決定（D 區 pkg1 第 8–18 條）**，本設計的處置：
   - 第 8 條（開啟時存基準、套用後前進）、第 11 條（新版直接對基準比、不逐版重播）、第 13 條（相依的主檔與整合一起比、缺相依列不能套）、第 14 條（系統管理員＋設計器；群組對應另要權限設定）、第 16 條（簽核中、簽核鎖定照設計器守衛擋）、第 17 條（「影響既有資料」分類與 mcp3 共用）、第 18 條（來源只分內建／匯入，發行者不當防偽）：照做。
   - 第 9 條（每個物件補穩定代號、要 migration）：不做。欄位、選項、區塊、報表、流程類物件已有對照列或 Key（§3）；規則與檢視依使用者 2026-11-21 裁決整組比對、名稱對應（Q7）。套件設計決策 10「一般欄位不存代號」早已被 `AppField` 對照表取代（s2c），不必再回寫。
   - 第 10 條（pkg1 前開啟的應用程式用目前版號對應的內建套件檔補登基準）：不做。目錄只有最新版，沒有舊版檔可對；使用者 2026-11-21 已裁決沒有基準一律當「可能改過」（§4）。
   - 第 12 條（`formatVersion` 升一版放版本與來源標記）：不做，依使用者 2026-11-21 裁決 Q9。
   - 第 15 條（基準版本＋各模組 RowVersion 當樂觀鎖）：改用 token（§8.3），涵蓋範圍更大（含非模組的物件與共用主檔），效果相同。

## 18. 測試重點

- **不變式 U1**：每個內建套件（含主檔、含 MES 的規則與檢視、進銷存的事件與分錄）開啟後同版預覽零差異。這是比對正規化的主要防線，放在 pkg1b，之後每次內建套件或格式改版都會跑到。**最大風險在這裡**：現況是從資料庫匯出、基準是原文，兩邊的寫法差異（預設值省略、選項值的寫法、公式代號、群組代號）只要漏一種，客戶就會看到一堆假差異，誤以為自己改過。
- **覆蓋率測試**（審查必修 4）：用反射列出 `AppPackageData` 以下每個 record 的屬性，加上 `FieldConfig` 的每個鍵；每一個都必須出現在比對對照表，或列在明文的「不比對」清單並附理由（排序 T7、`requires`、群組名稱、`x-` 附註等）。新增屬性沒歸類就失敗。放在 pkg1b，之後每次格式升版都會擋下沒補比對的那一段。實作（pkg1b 審查 M2）：從 `AppPackageData` 沿不比對的屬性往下走，走到的每個 record 必須恰好屬於整份比對或手工比對其中之一，手工比對的每個屬性都要在手工比對或不比對清單；清單裡的名字也必須是真的屬性（雙向）。`FieldConfig` 的鍵整份當 `config.<鍵>` 比，不另列。
- **U1 反向**：U1 只證明正規化沒比出假差異；反向是每條正規化至少一格「新版真的改了仍會列出」（pkg1b 先補 config 預設值、明細關聯、彙總、repeat、editable、approval、群組略過、權限-only 貢獻、區塊欄數、檢查欄位自動可篩選各一格，完整版放 pkg1c：對每個內建套件逐一改動每一種可比屬性，每種項目至少一個代表，比對引擎必須列出對應的差異與屬性名稱）。
- **U1 擴大**（審查建議 9）：開啟與匯出往返測試用的套件（`AppV3Tests` 一類的測試套件、v1 範本檔、省略預設值的寫法）也各跑一次「開啟後同版零差異」。
- **比對引擎直接測**（審查建議 6）：U1、U1b、U1c、A5 經 API 做不到（同版會直接回「已是最新」），從 Application 層的比對服務直接呼叫；A5 另備一份測試用 1.5.0 套件。
- **migration**（`Category=Postgres`，雙跑）：建表、cascade、兩個 JSON 欄的預設值；`MigrationConsistencyTests`。
- **分類引擎**（純函式單元測試）：§6.3 兩張表的每一格；多語逐語系；沒有基準；物件型項目的頂層屬性。
- **比對模式匯出**：停用欄位在、客戶新增的不在比對裡、表達不了的引用標「無法比對」而不是「客戶已刪除」。
- **套用**：U9–U24、A1–A21；回滾（A4、A21）；token（A3、A3b）；一般模組權限整份取代時不弄掉客戶自己的權限列；主檔與貢獻的權限走來源記錄（A19），權限頁手動改的 `Manual` 來源不被碰到。並行的 token 測試加 `Category=Postgres`。

- **既有測試**：`AppCatalogChecks`、開啟與匯出的往返測試（`AppV3Tests` 一類）、共用主檔合併測試都要照過；Demo 改了 CRM 的開啟方式，改前 grep 以 CRM 欄位、報表為斷言的測試（`CrmDesignCaseAppTests`、`DemoReportsTests` 等）。

- **pkg1d**：每個新原因代碼至少一格「預覽標無法套用」加一格「條件不成立時可以套」（A26–A38、A44、A56、A59–A61、A64、A66、A72；`flowInUse`、`transitionGroups` 的「可以勾」格在 A31、A28），`futureOnly` 見 A73；候選帶上相依閉包、不誤判新狀態與新流程（A25、A52、A56，T58）；守衛的唯讀判斷和設計器入口共用，各補一格「設計器照樣擋」防回歸，但一般唯讀狀態的解鎖是升級專用規則（T46 第 2 點），這一格改成「設計器照樣允許」；預覽不寫資料（A58）；組合違規的 409 回滾（A57）；狀態機第一趟不動既有需簽核（A51）、逐階段交錯（A52）；群組代號撞名（A53）；相依規則補強（A25、A54、A55、A63；新模組與新流程互相依賴的前端連勾 S5）；整合已安裝與沒安裝過兩條路（A43、A45、A66）、調和失敗不吞掉版號與基準（A67）；主檔並行（A3b，`Category=Postgres` 雙跑）、合併副本往返（A49）、客戶欄位不重建（A68，先寫失敗測試）、`masters` body 驗證（A69）、只有主檔有新版（A70）、上次略過的被依賴項目（A71）；U1 對第二批（含簽核備援頂替 T42、簽核流程拆出 `approvers` 屬性 T59）照跑；簽核流程留在 `AutoCompared`，覆蓋率測試不必改（T59）；主檔模組上的報表（A74）。

## 19. 待確認清單

### 19.1 行為類（裁決狀態逐題標明）

狀態用語：「使用者裁決」是使用者拍板的；「已確認（分流）」是 2026-11-19 平台分流的顧問裁決，使用者 2026-11-20 整區確認；「顧問拍板，待使用者確認」是這輪顧問分流的結果，還沒經使用者確認；「顧問定案（2026-11-22 pkg1d 顧問分流），待使用者事後確認」是 pkg1d 顧問分流（lifecycle:domain-advisor）依既有裁決與設計推得出結論的題，先照它做，使用者事後確認；「主控照顧問推薦暫定，待使用者確認」是分流找出的漏題，照推薦寫入。題目內容（例子、推薦、代價）保留，方便確認時直接看。

- **Q1 客戶刪掉、新版仍有的項目：標「客戶已刪除」、預設不勾。**
  - 狀態：顧問定案（2026-11-22 pkg1d 顧問分流），待使用者事後確認。依據：使用者 11-17 裁決「客戶改過的預設不覆蓋」；刪除就是客戶改過；只影響預設勾選。
  - 例子：客戶覺得 CRM 用不到「傳真」欄位，把它刪了；新版 1.4.0 還有「傳真」。更新頁這一項標「客戶已刪除」，不勾。
  - 推薦：預設不勾，想要回來的自己勾。代價：新版若修了這個欄位，客戶不會自動拿到，要自己勾。
  - 替代：當成新版新增、預設勾。代價：客戶刪過的欄位每次更新都被加回來，違反「客戶改過的預設不覆蓋」。
  - 選錯的代價：小，只是預設值，每項都能改勾。
- **Q2 同一個項目，客戶和新版改的是不同屬性：照「只有新版改」處理、預設勾，客戶改的屬性保留。**
  - 狀態：顧問拍板（與分流 pkg1-漏1 相同，使用者 2026-11-20 已整區確認，可不必再問）。
  - 例子：客戶把「預估金額」的繁中標籤改成「報價金額」，新版把它的小數位從 0 改成 2。推薦做法下這一項算「只有新版改」，套用後標籤仍是「報價金額」、小數位變 2。
  - 推薦：以屬性判斷衝突。代價：分類規則多一層，畫面要展開才看得出客戶改過哪個屬性。
  - 替代：只要客戶動過這個項目就算「兩邊都改」、預設不勾。代價：客戶改過標籤的欄位，之後的修正（小數位、長度）一律要手動勾，修正很容易被漏掉。
  - 選錯的代價：小，只是分類與預設。
- **Q3 略過的項目下次升級再列出，標「上次略過」、預設不勾、可以勾回。**
  - 狀態：使用者裁決 2026-11-21（照分流 pkg1-5）。取代初稿的「基準整份換新，略過的變成只有客戶改或客戶已刪除」。
  - 做法：基準原文仍整份換成新版；另在基準表的 `SkippedJson` 記這次可勾卻沒勾的項目與當時的舊值、新值（§9.2）。下次預覽時，客戶沒再動過的就標「上次略過」（§6.3）。仍只有 pkg1a 一組 migration。
  - 例子：1.4.0 有 10 項差異，管理員只套了 7 項。到 1.5.0 時那 3 項列在「上次略過」，預設不勾，顯示當時的值與這次新版的值，想要就勾回。
- **Q4 新版移除的項目：只列出「新版已不再提供」，不刪也不停用。**
  - 狀態：顧問拍板（與分流 pkg1-漏4 相同，使用者 2026-11-20 已整區確認，可不必再問）。
  - 例子：新版拿掉了「潛在客戶」的「傳真」欄位。更新頁列出這一項，不能勾，欄位與資料都留著；不要的話客戶自己到設計器停用或刪除。
  - 推薦：只列出。代價：客戶系統裡會留著原廠已淘汰的欄位。
  - 替代：可以勾「停用」，預設不勾。代價：多一種套用動作；停用影響規則、報表、公式的引用，要多一層相依檢查。
  - 選錯的代價：小，之後要加「停用」不影響既有資料。
- **Q5 既有模組的權限修改只列出、不能套用；新模組的權限照群組對應一起套，預覽中可以改群組對應（要有權限設定權）。**
  - 狀態：已確認（分流 pkg1-4，使用者 2026-11-20 確認）。取代初稿的「權限放寬沿用一般規則、預設勾並標示」；初稿的 `widensPermission` 一併拿掉（既有權限不能套，就不需要「放寬」標示）。
  - 理由：新模組沒有既有授權可衝突；既有授權是客戶的決定。
  - 例子：新版讓「業務」群組可以刪除報價單（既有模組）：更新頁列出這一項，不能勾，提示到權限分頁自己調整。新版新增「客服工單」模組並給「業務」讀取：照群組對應一起建好。
  - 落點：§6.2 說明第一點、§6.2.1、§6.4、§9.1 第 7 步、§10.2 第 3 點。
- **Q6 已關閉的應用程式不能更新，要先重新開啟。**
  - 狀態：顧問拍板（與分流 pkg1-漏3 相同，使用者 2026-11-20 已整區確認，可不必再問）。
  - 例子：客戶關閉了生產管理，原廠出新版。卡片只顯示「有新版」，滑過提示「重新開啟後才能更新」。
  - 推薦：要先重新開啟。代價：想在關閉狀態下先更新、之後再開的客戶要多一步。
  - 替代：關閉中也能更新。代價：關閉的模組擋下會改寫記錄值的設計器修改（`ClosedDataGuard`），新公式、換標題欄位會套用失敗，要另寫一套關閉時能套哪些的規則。
  - 選錯的代價：小。
- **Q7 規則以「一個模組的整組規則」為一個項目；共用檢視以繁中名稱對應。**
  - 狀態：使用者裁決 2026-11-21：規則整組比對、檢視用繁中名稱對應（維持初稿）。這推翻 2026-11-19 分流技術決定 9「每個套件物件補穩定代號、需要 migration」對規則與檢視的部分（§16 第 9 點）。
  - 背景：規則沒有代號，存檔時整批替換（`SaveRulesHandler`），系統分不出「客戶改的是哪一條」；檢視只有名稱。
  - 例子：生產管理的「工單」有 7 條規則。新版改了其中一條的條件、客戶沒動規則：整組換成新版的 7 條，預設勾。客戶自己加過一條：整組算「兩邊都改」，預設不勾，畫面列出三份規則清單讓管理員比，要採用新版就整組換掉（客戶加的那條要自己重加）。
  - 推薦：整組比對，不改格式、不加 migration。代價：客戶動過任何一條規則，那個模組之後的規則修正都要整組判斷。
  - 替代：規則與檢視加持久代號（格式升版、資料庫加欄位、設計器存檔要保留代號）。代價：多一次格式升版和 migration，設計器的規則畫面要改；好處是能逐條套用。
  - 選錯的代價：中。之後要改成逐條，要加格式與 migration，但基準是原文，不必搬資料。
- **Q8 新版新增的必填欄位：模組已有記錄時改成非必填並警告；新版把既有欄位改成必填、而有記錄沒填：列出、不能勾，引導到設計器。**
  - 狀態：前半是技術決定 T13（同 `MasterMerger`）；後半已確認（分流 pkg1-3，使用者 2026-11-20 確認）。取代初稿的「既有欄位改必填照套並警告」。
  - 例子：新版把「報價單」的「有效期限」改成必填，200 張裡 30 張沒填：更新頁列出這一項，不能勾，原因「會影響既有資料：30 筆沒有值，請在設計器手動處理」，附「到設計器」連結。全部都有填時照一般規則可以勾。
- **Q9 新版的來源與「來源標記」：不改套件格式，用既有的 `manifest.version` 加開啟時記下的來源（內建／匯入）；內建開的只能用內建新版更新，匯入的再匯入較新版本時取代舊的那份。**
  - 狀態：使用者裁決 2026-11-21：來源標記不改格式，由 `manifest.version` 加 `App.Source` 落實 11-17「套件格式要帶版本與來源標記」的裁決（§7.1、§7.2）。這推翻 2026-11-19 分流技術決定 12 的「`formatVersion` 升一版，放版本與來源標記」（§16 第 9 點）。發行者（`manifest.vendor`）只是自我宣稱，不當防偽依據，手冊寫明（分流技術決定 18）。
  - 背景：使用者 11-17 裁決「套件格式要帶版本與來源標記」。格式裡早就有必填的 `manifest.version`，來源記在 `App.Source`，所以推薦不加新欄位。
  - 例子：廠商給的「ACME CRM」1.0.0 已開啟，廠商寄來 1.1.0，管理員到應用程式頁匯入，卡片出現「有新版 1.1.0」。有人拿一份自稱 `crm-sales` 的檔案來匯入，被擋（409）。
  - 推薦：如上。代價：匯入的舊版原文不留，還沒開啟的人只能開新版。
  - 替代：格式加 `manifest.origin`（發行者代碼）並比對。代價：格式升版；發行者代碼沒有簽章，擋不了刻意偽造，只是多一個欄位。
  - 選錯的代價：小，之後要加簽章或發行者代碼再升格式即可。
- **Q10 共用主檔的新版：跟著使用它的應用程式的更新頁一起列出、一起套用。**
  - 狀態：顧問定案（2026-11-22 pkg1d 顧問分流），待使用者事後確認。依據：平台先例：共用主檔不在應用程式清單，由使用它的應用程式自動開關（手冊 §18「誰能做」）；pkg1b 已照此上線（直接預覽主檔回 `MasterManaged`）。
  - 背景：共用主檔不在應用程式清單裡（手冊 §18「誰能做」第 3 點），由使用它的應用程式自動開啟。
  - 例子：「往來對象」1.0.1 → 1.1.0 多了「傳真」欄位。CRM 的更新頁多一段「共用主檔『往來對象』1.0.1 → 1.1.0」；CRM 本身沒有新版時，CRM 卡片也顯示「共用主檔有新版」。進銷存也用往來對象，從進銷存的更新頁也看得到同一段，誰先套用都可以，套完另一頁就不再列。
  - 推薦：如上。代價：同一份主檔出現在多個更新頁。
  - 替代：把主檔放進應用程式清單，只在有新版時出現。代價：清單規則多一個例外，主檔的群組、權限要另外解釋。
  - 選錯的代價：小，只影響入口位置。
- **Q11（撤回）開啟時略過的群組，升級時要不要再問對應。**
  - 狀態：撤回，由分流 pkg1-4「預覽中可改對應」涵蓋，不再單獨問。
  - 重新評估：初稿的 Q11 是在「預覽不能改群組對應」的前提下問的。pkg1-4 讓預覽可以改對應之後，略過的群組只影響新模組、新物件的權限（既有模組的權限本來就只列出），所以做法定為：新物件用到略過過的群組時，群組段列出它、預設維持略過、可以改（§6.2.1 第 3 點、§10.2 第 3 點）。已經對應好的代號不能在預覽改（技術決定 T26）。
- **Q12 新版在既有模組加的新欄位、新選項、新貢獻，附帶的權限跟著新物件一起套，含給權類；給權記在應用程式名下，關閉時收回。**
  - 狀態：使用者裁決 2026-11-21。
  - 例子：新版在既有的「報價單」加「成本價」欄位，套件同時寫「業務」群組看不到它：欄位和這條隱藏一起建，預覽那一列標「業務：隱藏」。CRM 新版在往來對象的貢獻上加「信用額度」欄位、給「業務」可編輯：一起套，預覽標「業務：可編輯（給權）」；記在 CRM 名下，CRM 關閉後這條編輯權不再生效。
  - 落點：§6.2 說明、§8.4 `attachedPermissions`、§9.1 第 7 步、§10.2 第 5 點、U27、U28。

以下 Q13–Q27 是 pkg1d 新增（2026-11-22），落點在 §9.6。Q13–Q25 經 pkg1d 顧問分流定案（Q16 修正後定案），待使用者事後確認；Q26、Q27 是分流找出的漏題，照推薦寫入，待使用者確認。

- **Q13 新版移除或改名的狀態，仍有記錄停在那裡：舊狀態與它的轉移保留、只列出；新狀態照加；記錄不搬。**
  - 狀態：顧問定案（2026-11-22 pkg1d 顧問分流），待使用者事後確認。依據：「只新增不刪除」（11-17）與 Q4（pkg1-漏4）；不搬記錄才不繞過轉移、事件、事實鎖。衍生漏題 Q26。
  - 例子：進銷存 1.3.0 把出貨單的「已作廢」改名成「已取消」（套件裡是拿掉選項 `void`、新增 `cancelled`）。客戶有 5 張單在「已作廢」。更新頁列「已作廢」為「新版已不再提供」，註明「目前 5 筆記錄在這個狀態」；「已取消」與它的轉移是新版新增、預設勾。套用後兩個狀態都在，5 張單仍是「已作廢」，要不要改成「已取消」由客戶自己走轉移或手動處理。
  - 推薦：如上。代價：狀態機多一個原廠已淘汰的狀態，報表與檢視要客戶自己整理。
  - 替代 A：預覽提供「舊狀態 → 新狀態」對應，套用時批次改記錄的狀態。代價：繞過轉移、事件、簽核與事實鎖，等於升級在改客戶的資料，違反只新增不刪除的精神。
  - 替代 B：有記錄停在被移除的狀態就整個擋下。代價：客戶升不了級，只能先手動清空那個狀態。
  - 選錯的代價：小。之後要加對應工具不影響既有資料。

  - 推薦：任一關的簽核人或流程的備援簽核人，新版與目前不同、而且不是只有客戶改（含沒有基準的應用程式，複核 N4），整項標無法套用（`approverGroups`），原因「簽核人是你的內控決定，請到簽核流程設計器調整」；新版的關卡增減會讓客戶自己加的關卡或簽核人配不上（關卡代號集合不同），同樣不能套（複核 N3）；只改關卡名稱、條件照常可勾。新增的流程不受限制。代價：比對要把關卡拆成簽核人與其他內容兩部分（§9.6.2）；原廠修正簽核人的錯送不到客戶，要客戶自己改。
  - 替代 1：照一般屬性預設勾，預覽標「改變簽核人」。代價：原廠更新可能在客戶沒注意時放寬誰能核准。
  - 替代 2：整份關卡清單一律只列出。代價：連關卡名稱的翻譯修正都送不到；§9.6.5 的 Demo「關卡名稱換舊」要改。
  - 提醒：既有報表的分享群組在 pkg1c 已照一般屬性上線，也是授權；採推薦的話，另開票讓報表分享比照（§22.2）。
  - 選錯的代價：小，只影響能不能勾。
  - 落點：§9.6.2 簽核流程、§9.6.4、§9.6.6、A64。

## 20. 宗旨檢查（formwright-purpose-check）

1. **機制還是政策**：通過。比對、分類、相依、交易都是平台機制。預設勾不勾、能不能套是使用者裁決或顧問拍板的平台規則（§4、§19.1），不是各客戶不同的業務政策。沒有新增上限或天數；新版的數量上限沿用 `PackageLimitReader` 讀的既有政策。
2. **寫死掃描**：設計階段不適用；新的寫死項目列在 §21，審查 diff 時照 skill 的 grep 再跑。
3. **單一來源**：通過。上限沿用 `PackageLimitReader`；分類、預設勾選、能不能套用只在後端算（`defaultSelected`、`applicable`），前端照回應顯示，不自己再判斷一次；套件的候選來源只有一個函式（§7.1）；「會不會影響既有資料」的分類與 mcp3 共用（§6.4）。
4. **兩個應用程式**：通過。CRM、進銷存、生產管理、兩份共用主檔、客戶匯入的套件都走同一條路。
5. **空系統**：通過。沒開任何應用程式時應用程式頁沒有「有新版」，平台照常；基準表是空的。
6. **套件只用定義組成**：通過。升級只是「用既有設計器指令把新版的定義補進來」，沒有替特定應用程式開後門；Demo 的舊版是由目錄版推導，不是特製套件。
7. **ERP 對照**：通過，見 §14。
8. **權限 fail closed、驗證不只在前端、沒有執行期 DDL**：通過。預覽與套用都要系統管理員，套用再要權限設定；既有模組的權限不會被升級改動，新模組的權限只給對應到的群組；相依、token、可套用與否都在後端驗；新群組沒對應就略過（同開啟的 fail closed）；schema 變更只有 pkg1a 的 EF migration。
9. **不限產業**：通過。理由是「原廠修正要送到已客製的客戶手上」，服務業（客服工單套件）、貿易商（進銷存）、批量工廠（生產管理）都一樣。

**pkg1d 第二批（§9.6，2026-11-22 自查）**：

1. **機制還是政策**：通過。逐類套用與「不能套」的判斷大多來自既有設計器守衛（T32、T47）與資料完整性（已觸發的效果代號、已有記錄的分錄、簽核中的轉移、已轉出的單據）；比設計器嚴的兩條是升級專用的平台規則：一般唯讀狀態的解鎖（Q14，資料完整性）、既有簽核流程的簽核人只列出（Q27，安全檢查）。都不是各客戶不同的業務政策；用到的數字只有既有政策 `check.maxBackfillRecords` 與 `approval.defaultFallbackApprovers`，沒有新上限、天數或預設值。

3. **單一來源**：通過。守衛的判斷抽成一份唯讀函式，設計器入口與預覽共用（T32）；`applicable`、`impacts` 只在後端算。
4. **兩個應用程式**：通過。狀態機、簽核流程、轉換、列印範本、貢獻：CRM 與進銷存都有；事件、檢查、分錄：進銷存與生產管理都有；任務規則：CRM 有，任何套件都能帶（任務設計 §5.8）；整合：目前只有生產管理帶一個，但它是平台既有的通用格式（整合設計），升級路徑不看是哪個整合。
5. **空系統**：通過。沒有任何應用程式時沒有更新頁；主檔段只在用到它的應用程式有新版或主檔有新版時出現。
6. **套件只用定義組成**：通過。新物件走開啟同一條 `AppFlowInstaller`，修改走設計器指令，沒有替特定應用程式寫分支；Demo 的舊版仍由目錄版推導。
7. **ERP 對照**：通過，見 §9.6.6。
8. **fail closed、驗證不只在前端、沒有執行期 DDL**：通過。新轉移的群組全略過時不建；既有轉移的群組、既有簽核流程的簽核人、既有權限只列出；群組代號在 id 層合併，不會因代號撞名給錯群組（T44）；客戶改過的整合不覆寫；相依、守衛、token 都在後端驗；沒有 migration。
9. **不限產業**：通過。例子用了出貨、採購、報價、設計案，服務業（設計案、客服）與貿易商（進銷存）都適用；理由不假設製造流程。
